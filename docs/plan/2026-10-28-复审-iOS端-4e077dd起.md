## 1. 新缺陷

### N-1｜P2：meta 残留 + .bin 丢失后，该曲永远不会再被缓存
- 位置：ios/SuenMusic/Player/AudioCacheStore.swift:186-193（download 的 begin 判定）vs :72-85（cachedFileURL）
- 证据：
  ```swift
  // download（:188-190）
  if index[trackId] != nil { return false }        // meta 存在就拒绝
  // cachedFileURL（:76-80）
  guard let meta = index[trackId], meta.trackId == trackId else { return nil }
  guard let size = fileSize(bin), size > 0 else { return nil }   // bin 不在 → nil
  ```
- 为什么错：`download` 的防重入口看的是 **meta 索引**，`isCached` 看的是 **.bin 实体**。
  一旦出现「meta 在、.bin 被用户手动删/文件系统丢/写盘中断」（引擎 :1126 `isCached` 返回 false），
  `startCacheDownloadNow` 调 `download` 会被 ：188 拒掉返回 nil，且没有任何路径 evict 这条死 meta ——
  该曲从此既播不了缓存也永远缓存不回来，直到用户整页清空。
- 修复建议：begin 判定改为 `if isCached(trackId) { return false }`（即以 .bin 实体为准）；
  或 `loadIndexLocked` 时对缺 .bin 的 meta 顺手 removeLocked。

### N-2｜P2：随机模式下连点「下一首」的乐观推进走数组顺序，会切到非播放顺序的曲子
- 位置：ios/SuenMusic/Player/PlaybackService.swift:429-448（nextTargetIndex / previousTargetIndex）、:464-490（jumpTo）
- 证据：
  ```swift
  if queue.indices.contains(pendingTargetIndex) {
      let stepped = pendingTargetIndex + 1        // ← 数组下标 +1
      return queue.indices.contains(stepped) ? stepped : nil
  }
  ```
- 为什么错：乐观推进（I-2 修复手段）只在顺序模式下与引擎的 `nextLogicalIndex()` 一致。
  随机模式下下一首由引擎的 `playOrder` 决定（AudioEngine.swift:924 起），不是 index+1。
  连点两次「下一首」：第二次的目标 = 第一次目标 +1（数组序），解析回来若代际号仍最新就会落地到
  一首 playOrder 之外的歌 —— 用户听到的不是随机序列中的下一首。
- 修复建议：pendingTargetIndex 记「解析中目标」即可，第二次点击仍用引擎 `nextLogicalIndex()` 的结果，
  但把去重口径从「下标」改成「代际号 + 目标 id」；或 pendingTargetIndex 存 playOrder 意义上的步数。

### N-3｜P3：warm() 预热不带 quality，预热键与播放键不一致
- 位置：ios/SuenMusic/Player/PlaybackService.swift:322-330
- 证据：`_ = try? await APIClient.shared.resolve(trackId: track.id)`（:327，无 quality 参数）
  vs play/jumpTo/prefetchNextDirect 都带 `quality: requestQuality`。
- 为什么错：预热请求在服务端按缺省档解析并落 `play_sources` 行（服务端 S-1/S-2 的另一入口），
  与之后带 quality=exhigh 的播放解析不同键 → 预热大概率白打；更坏的情况是给服务端写进一条
  非目标档位的缓存行，被 shape() 旧键读取路径命中（正是 S-1 描述的最坏路径的制造者之一）。
- 修复建议：warm 也带 `quality: requestQuality`；或等服务端 S-1/S-2 键收敛后再评估。

### N-4｜P3：directLinks 只增不减，跨队列残留
- 位置：ios/SuenMusic/Player/AudioEngine.swift:69、:80-102、:316-405（setQueue 未清理）
- 为什么：setQueue/rebuildQueue 均不清 `directLinks`，换歌单后旧曲目的直链一直留到过期。
  有 expiresAt 兜底、无功能危害，只是内存与 hygiene 问题。
- 建议：setQueue 整队重建分支里 `directLinks.removeAll()`（当前曲的直链在 resolve 后会重新写入）。

### N-5｜P3：RootView.swift:76 注释仍引用已删除的 widget
- 位置：ios/SuenMusic/UI/RootView.swift:76 ——「对应 widget 的 .widgetURL」。
  Widget/Live Activity 已在 60ecdcd 彻底移除，注释成了误导（I-10 的残余，README 已改、这处漏了）。

### N-6｜P3：缓存页用量统计在主线程同步 stat 全部文件
- 位置：AudioCacheStore.swift:93-103（usedBytes 对每个 id 做 attributesOfItem）、:109-118（entryCount 同）、CachePage.swift:168-172（onAppear 主线程直接调）。
  条目量 ≤ 1GB/10MB ≈ 100+ 时单次 onAppear 一百多次 stat，尚可接受，但 `entries()` + `usedBytes`
  一次刷新会 stat 两遍。建议 refresh 里合并成一次遍历或挪后台。
