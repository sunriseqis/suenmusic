### 2.2 酷狗 crypto.ts / simulate.ts 移植正确性 ✅（静态比对）

- crypto.ts：AES-256-CBC，key = md5(16位随机串) 前 32 字符按 UTF-8 当 32 字节密钥，iv = key 尾 16 字符，hex 输出 —— 与参考实现 crypto.js:188-213 语义一致；RSA 为教科书式无填充（`RSA_NO_PADDING`，右侧 \0 补齐到模长，hex 输出），1024 位 LITE 公钥与标准版公钥分常量存放，切换点单一。params/pk 出自同一次 `cryptoAesEncrypt`（kugou-verify.ts:encryptPair），链路闭合。
- simulate.ts：AES-128-CBC + 固定 IV "kugousecurity123"（16 字节，与 createCipheriv 要求吻合），key = md5(randomString(16)) 前 16 字符；RSA-OAEP-SHA256 加密 AES key → sid，Base64 输出；事件串格式（type-3/5/6 + 哨兵 + 贝塞尔轨迹 + 每 12 帧插滚动）与明文拼接 `mid=..;userid=..;dfid=..;webgl=..;webdriver=0;ts=..;data=..` 均按参考实现逐项对齐，注释明写「换公式等于换指纹」。
- 两把公钥职责分离有明确注释（1024 位加密 params vs 2048 位酷狗服务端解 SID），不会混用。
- 未实测（文档已如实标注「未做真人验证实测」），静态层面移植忠实。

## 3. 新发现缺陷

### S-16｜P3：代理兜底路径的档位键残留漂移（S-2 的尾巴）

- 位置：server/src/routes/stream.ts:373（读 `cacheKeyFor(trackId, preferMp3)`）、:503（兜底 `resolveTrack(..., { force: urlExpired, preferMp3 })` 不带 quality）。
- 影响：iOS 直链失效回退代理时，代理读不到 `:mp3:exhigh` 行（必 miss 重解析），重解析结果写 `:mp3` 键；iOS 下次 resolve 读 `:mp3:exhigh` 仍是旧地址（该地址其实已被上游 403，会再触发一轮失效重解析）。不再错配 directUrl/Headers（shape 精确键读取），纯效率/新鲜度问题。
- 建议：代理兜底 resolveTrack 时带上从 URL query 透传的 `quality`（streamUrl 由服务端签发，可在 buildStreamUrl 里捎带归一化后的档位）；或代理读键时按档位降级试探（`:mp3:<q>` → `:mp3`）。

### S-17｜P2：send-sms 服务端零频控，票据窗口内可短信轰炸

- 位置：server/src/routes/kugou-verify.ts:66-73（只校验手机号格式，无任何频控）；60s 冷却仅存在于 web/src/views/KugouVerify.vue:229-236（前端可绕）。
- 影响：持有效 t（30 分钟）者可对同一手机号高频触发上游 send_mobile_code：骚扰机主、耗尽酷狗配额、甚至给服务端 IP 招风控。
- 建议：服务端按 eventId（或手机号）做 60s 间隔限频 + 每 30min 上限（如 5 次），超限 429。

### S-18｜P2：酷狗 SVIP 的 availableQualities 与请求序列不同源，「高」档声明可点实际拿 128k

- 位置：server/src/sources/kugou/stream.ts:466-475（qualityOrder：reqQ==='standard'||'high' 一律 `['128']`）、:482-489（availableQualities：svip 且有 320 goods 即 push 'high','exhigh'）。
- 影响：svip 用户请求 quality=high → 尝试序列锁 ['128']，命中后 currentQuality='standard'；但响应 availableQualities 含 'high' → UI 把「高」点亮，点了拿到的仍是 128k 并显示「标准」。违背 doc1 §三.2 置灰闭环的语义（声明档必须真能以该档生效）。
- 建议：qualityOrder 对 reqQ==='high' 给 `['320','128']`（酷狗 320→exhigh 映射，严格说酷狗没有独立的 192k 档——那么应把 'high' 从酷狗 availableQualities 里去掉，或声明时注明「高=320」）；两列表必须由同一张能力表推导。

### S-19｜P2：unknown 态下 SVIP 被按「仅 128」处理且 availableQualities 报 ['standard']

- 位置：kugou-status.ts unknownState() 恒 `svipActive: false`；stream.ts:466 `if (!svip) qualityOrder = ['128']`、:482 availableQualities 只 push standard。
- 影响：网络抖动 30s 窗口内（S-8 修复引入），SVIP 用户的解析被降成 128k 尝试序列，且可用档被报成只有 standard —— 与 unknown「临时抖动不该降低体验」的设计意图相悖。
- 建议：unknown 态沿用「上次已缓存的 vip 快照」（kugou-status 已有 STATUS_CACHE_TTL_MS 缓存，可让 unknown 复用最后一份成功判定的 svipActive），或 unknown 时按宽序列尝试、由逐档试听判定兜底。

### S-20｜P3：HMAC 票据密钥随 jwtSecret 逐进程随机，重启即全量失效

- 位置：kugou-verify.ts:489（`config.jwtSecret`）、config.ts:235（未配置时 randomBytes）；stream-token 同源（行为一致，可视为既有约定）。
- 影响：未配置 `SUENMUSIC_JWT_SECRET` 的部署里，手机通知里的验证链接在服务重启后 401。低危（验证本就短期），但与「系统浏览器打开通知链接」的使用路径叠加，容易踩。
- 建议：部署文档写明须持久化 `SUENMUSIC_JWT_SECRET`；或票据密钥单独一个可持久化配置。

### S-21｜P2：ssa-code 缺失时仍登记空事件，用户被引进注定失败的验证页

- 位置：kugou/stream.ts:352-358（`noteKugouVerifyEvent(ssaCode, ...)` 对空串照登）；kugou-verify.ts:154-171（eventId='' 也建事件）→ refresh :236-240 报「上游未回传验证事件 id」、submit :313-319 拦截。
- 影响：verifyUrl 照常下发（resolve.ts:69 `verifyRequired && isKugouVerifyPending()`），用户打开页面 → refresh 永远失败，整个流程死路。
- 建议：noteKugouVerifyEvent 对空 eventId 直接 return（不登记），reason=need_verification 仍可下发但 pending=false，客户端提示「服务端未取得验证事件，请重试」。

### S-22｜P3：验证事件为模块级单例，并发第二次 20028 覆盖进行中的验证

- 位置：kugou-verify.ts:130 `let currentEvent: VerifyEvent | null`。
- 影响：多用户/多设备同时撞 20028 时后来者顶掉前者（sessionId 重置、前者票据指向的事件被换）。当前单用户部署无实害。
- 建议：以 eventId 为键存 Map（仍是内存 + 30min TTL），或文档明示单事件设计。

### S-23｜P3：网易云 availableQualities 是账号级而非曲目级

- 位置：netease/source.ts:127-137（`neteaseAvailableQualities(vip, preferMp3)` 取 lossless 最宽序列映射，与单曲实际版权无关）。
- 影响：VIP 账号 + 无损版权的单曲恒报 4 档；无该曲 FLAC 版权时点「原声」会静默降级到 exhigh（currentQuality 如实报，无谎报）。属声明粒度问题，非功能错误。
- 建议：暂可接受；若要闭环，需在 fetchPlayableUrl 里对每档探测后回填真实能力（成本是多次上游往返，不建议现在做）。

## 4. 「做对了」清单（本轮增量，勿动）

1. **cacheKeyFor 唯一键入口 + 写读同源 + 前缀级联清理**：S-1 全链路（单曲/锚点/批量/内存/DB/负缓存）一次修干净，注释把「为什么必须唯一」写透（resolver.ts:85-102）。
2. **quality 归一化单点化**：QUALITY_WHITELIST + normalizeQuality 同时服务单曲与批量，非法值既不 400 也不进缓存键，平台缺省与 doc2 §四.1 一致。
3. **音质落库**（迁移 023 + repo 列 + rowToResult 不猜后缀 + shape「宁可少报绝不虚报」的保守口径）：S-3 的根因级修复，置灰闭环的信息基础成立。
4. **preferMp3 语义归位**：B 站不再因 preferMp3 降 64k；网易云把 lossless/hires/jymaster 从候选真剔除并与 availableQualities 同源推导；higher→high 映射修正。
5. **platform.ts 身份与容器诉求拆分**：isIosClient / wantsMp3 各司其职，限速豁免不再可被 ?format=mp3 绕过。
6. **酷狗状态机升级**：unknown 态 + kugouUsable + 30s transient 负缓存，网络抖动不再谎报 ok 也不再误跳过整条源；tvip 白名单保留。
7. **20028 链路的克制设计**：取流层只登记不改失败语义；resolve 只在「本次解析确因 20028 失败」时下发 need_verification + verifyUrl（verifyRequired 由酷狗取流层置位、随结果落负缓存、验证通过后 deleteNegativeSources('kugou') 清理）—— 不会把 B 站失败误标成要验证。
8. **验证事件与票据同寿命（30min）、惰性过期、同 eventId 续期不重置 sessionId**；票据 HMAC + 长度检查 + timingSafeEqual。
