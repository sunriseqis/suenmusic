### S-1｜缓存键错配：响应里的 directUrl 可能来自**另一个音质档位**的另一行缓存 ✅

- 位置：server/src/routes/resolve.ts:61-63（读）；server/src/services/resolver.ts:203-204、:428（写）；server/src/services/resolver.ts:523（锚点路径写裸键）；server/src/db/repo/sources.ts:201-202
- 证据：

    // resolve.ts:61-63  —— 读：永远用「不带 quality 后缀」的裸键
    const row = outcome.ok
      ? (preferMp3 ? (getSource(outcome.trackId + ':mp3') ?? getSource(outcome.trackId)) : getSource(outcome.trackId))
      : null;

    // resolver.ts:203-204 —— 写：cKey 带 :mp3 与 :quality 两段后缀
    const qPart = quality ? (':' + quality) : '';
    const cKey = preferMp3 ? (key + ':mp3' + qPart) : (key + qPart);

    // resolver.ts:428 —— 结果存在 cKey 上
    saveSource(cKey, result);

    // resolver.ts:523 —— 锚点路径却把带具体档位的成功结果写到裸键
    saveSource(key, enriched);

- 为什么是 bug：带 quality 的请求（改完之后 iOS 必带）解析结果落在 qq_x:mp3:exhigh，而 shape() 只读 qq_x:mp3 / qq_x。
  只要该曲此前被「不带 quality 的路径」写过一行——/api/stream 代理兜底重解析、批量解析接口、锚点路径——shape() 就会取到那一行，
  并用它覆盖本次解析的正确答案：
  1. directUrl 变成 row.audioUrl（旧档位/旧音源 URL），本次精心解析的 outcome.sourceUrl 被丢弃在旁；
  2. directHeaders 由 row.source 决定，可能与真实 URL 不匹配（酷狗地址配 B 站 Referer）；
  3. source 音源角标被旧行改写。
- 最坏路径：iOS 先走一次 /api/stream 兜底 → 代理侧不带 quality 解析，网易云黑胶 VIP 此时直接给 FLAC（见 S-6）并存进 qq_x:mp3 →
  之后任意一次 iOS resolve(quality=exhigh) 都把这条 FLAC 当 directUrl 下发 → AVPlayer 播 HTTP 裸 FLAC → 无声。
- 修复建议：把缓存键收敛成唯一一个函数 cacheKeyFor(trackId, {preferMp3, quality})，写与读都调用它；
  或让 resolveTrack 回传实际落库键（ResolveOutcome.key），禁止调用方再自行拼接。

### 顺带：这条根因直接导致 directExpiresInSec 恒为 0（跨端连锁）

- server/src/routes/resolve.ts:115-122 ✅：

    directUrl: directEnabled() && outcome.ok ? (row?.audioUrl || outcome.sourceUrl || null) : null,
    directExpiresInSec: directEnabled() && row ? Math.max(0, Math.round((row.expiresAt - Date.now()) / 1000)) : 0,

  因为 row 读的是裸键，带 quality 的请求**首次必然读不到行**（结果被写进了带后缀的 cKey），于是 directExpiresInSec = 0。
- 端侧把这个 0 当有效值消费：
  - iOS ✅ ios/SuenMusic/Player/PlaybackService.swift:319：expiresInSec: r.directExpiresInSec ?? 3600 —— ?? 只挡 nil，挡不住 0。
  - 鸿蒙 ✅ hw/entry/src/main/ets/core/MediaPlayerCore.ets:1002：Date.now() + Math.max(0, (r.directExpiresInSec ?? 0)) * 1000 → expiresAt = now；
    立刻在 :981 的 cached.expiresAt > Date.now() + 60_000 判定中失效 → 每次起播和每次切歌都重新打一次上游解析。
- 结论：这条比单独报三个「0 秒过期」更准确，**修 S-1 即可一并消掉**；但要保留两端的防御（见 I-4 / H-3）。

### S-4｜quality 参数无白名单、无平台缺省钳制 ✅

- 位置：server/src/routes/resolve.ts:239、:254
- 证据：

    ...

- 为什么是 bug：doc2 §四.1 明确「不传 quality 时 iOS 为 exhigh、其他为 lossless」，代码里没有任何地方做这个钳制，

### S-5｜B 站：iOS（preferMp3）被无条件降成最低码率，且这是本次引入的回归 ✅

- 位置：server/src/sources/bilibili/stream.ts:374-390
- 证据：

    const wantStandard = options.quality === 'standard' || Boolean(options.preferMp3);
    const chosen = wantStandard ? sorted[sorted.length - 1] : sorted[0];

- 为什么是 bug：doc1 §二.1 的语义是「用户选 standard 才拿最低档，选更高才拿最高档」，

### S-6｜网易云：preferMp3 在档位选择里彻底消失，iOS 可能真的拿到 FLAC ✅

- 位置：server/src/sources/netease/source.ts:92-107（档位序列）、:191-194（可用档）
- 证据：

    function computeNeteaseLevels(vip: boolean, quality?: string): string[] {   // 没有 preferMp3 入参
      if (q === 'standard') { return ['standard']; }
      if (q === 'high')     { return ['standard', 'exhigh']; }
      if (q === 'exhigh')   { return ['exhigh', 'standard']; }
      if (q === 'lossless') { return vip ? ['lossless','exhigh','standard'] : ['exhigh','standard']; }

    ...

- 为什么是 bug：改动前 fetchPlayableUrl 里有 preferMp3 ? ['exhigh','standard'] : ...，本次重写后 preferMp3 只在 availableQualities 里还留着，

### I-2｜jumpTo 先 await 解析再起播：连点「下一首」只前进一首，且同一首会被从 0 重建两次 ✅

- 位置：ios/SuenMusic/Player/PlaybackService.swift:273-282、:304-332
- 证据：

- 修复：jumpTo 内先乐观推进（pendingTargetIndex + generation），落结果前校验 self.generation == gen 且引擎位置与预期一致；否则丢弃。

- 附带契约冲突（**2026-10-28 已裁定**，见第 7 节）：doc1 §一.2「本地缓存拥有绝对最高优先级，不管当前选什么音质」 vs doc2 §2.1「下一曲自动按新音质档位拉流」——
  同一个场景两份文档给出相反指令，代码选择了前者，于是后者落空。
- 修复（**2026-10-28 已裁定：缓存绝对优先、UI 不许说谎**）：
  1. 缓存命中永远秒播，哪怕文件只有 128k，**不得**因为 prefQ 更高就弃用缓存改走网络；
  2. 落缓存时把实际 quality 写进 .meta，fd 分支用它刷新 K_CURRENT_QUALITY；
  3. UI 如实显示实际档位（128k 就显示「标准」），这是本条唯一要改代码的地方；
  4. 同步修正 doc1 §一.2 与 doc2 §2.1 的矛盾表述，写死「缓存优先 + 如实展示」。

## 9. 建议修复顺序

1. **S-1 + S-2**（缓存键收敛为一个函数）：一名改动，同时消掉 directUrl 错档、directHeaders 错源、directExpiresInSec=0、I-4、H-3 的连锁症状。
2. **S-4 + S-5 + S-6**（quality 归一层 + 恢复 preferMp3 语义）：直接决定 iOS 会不会再踩「FLAC 无声」和「音质倒退」。
3. **H-1 + I-2**（两端 await 后的代际校验）：唯一会让用户「听到错误的歌」的一类，风险最高。
4. **S-3**（给 play_sources 加音质列）：置灰闭环能否成立取决于它。
5. **I-1**（直链提前到建 item 之前）：性能与带宽，改动面最大，可放最后。
6. 其余 P2/P3 按端分派清理。
