## 1. 新缺陷报告（H-15 起）

### H-15｜P2｜pause() 在 25 秒窗口内撤销待发下载 —— 是合理实现还是违反规格 2.2，需要用户裁定
- 位置：MediaPlayerCore.ets:481-482（pause 里 `clearCacheTimer()`），注释自称「规格 2.1」。
- 证据：规格 2.2 写「启动前**不做任何播放状态检查**：不做卡顿检测、不做带宽让路判据」；代码却在 25 秒到点前因暂停而作废定时器（:690-709）。
- 分析：规格 2.1 只说「起播后 25 秒才发起」，未规定 25 秒内暂停怎么办。当前实现是「暂停=作废待发、已发起不打断（:481 注释）」，与 2.3「一口气下完」不冲突，但**它确实是一种播放状态检查**，字面上与 2.2 有张力。
- 建议：不改代码，请用户确认口径；若认可，在规格 §2 补一句「25 秒内暂停则作废待发」。

### H-16｜P3｜loadCurrent 早退路径泄漏 pendingFile 的 fd
- 位置：MediaPlayerCore.ets:955（buildUrl 打开缓存文件并塞进 `this.pendingFile`）→ :974（`if (mySeq !== this.seq) { return; }`）。
- 证据：:977-980 只在通过 seq 复检后才消费 pendingFile；早退时 pendingFile 已持有一个打开的 fd。下一次 loadCurrent 的 buildUrl 会再次 openSync 并**覆盖** pendingFile（:1292），旧 fd 无人关闭。
- 触发：缓存曲目 3 秒内连点切歌（正好是 H-1 修过的同一窗口）。
- 建议：早退分支里若 `this.pendingFile !== null` 且未消费，直接 closeSync 并置 null；或在 buildUrl 打开前先 releaseOpenFile。

### H-17｜P3｜直链成功分支 `setMediaSource` await 后无 seq 复检（H-1 修复的残余窄缝）
- 位置：MediaPlayerCore.ets:998-1005。
- 证据：:992 在 `resolveDirect` 之后复检了 seq，但 :999 `await p.setMediaSource(ms)` 之后、usedDirect=true 分支没有再复检。若 await 期间用户切歌：新任务 reset 后，旧任务的 setMediaSource 要么抛异常（被 catch → 走 :1009 复检返回，安全），要么把上一首直链灌进刚 reset 的播放器并停在 initialized —— 新任务的看门狗 6 秒后 fail → 回退代理重载，**能自愈但会听到一段错源/多等一轮**。
- 建议：与 :1009 对称，在 try 块内 setMediaSource 成功后再加一次 `if (mySeq !== this.seq) return;`（并考虑对 idle 化的 player 补一次 reset）。

### H-18｜P3｜OfflineCache.quotaBytes 注释写「2GB 常量」，实际 QUOTA_BYTES = 1GB
- 位置：OfflineCache.ets `quotaBytes()` 头注释「配额（2GB 常量，UI 显示用）」vs :QUOTA_BYTES = `1 * 1024 * 1024 * 1024`（规格 6.2 正确是 1GB）。
- 建议：改注释，防止后人「修正」常量。

### H-19｜P3｜PlayerPage.qualityOptions 仍硬编码四档 key，未引用 QUALITY_LEVELS
- 位置：PlayerPage.ets:54（`qualityOptions`）vs Models.ets QUALITY_LEVELS（清单 H-13 声称的「唯一真源」）。
- 说明：H-13 主体已修（Models 有了真源、README 已改），但播放页的档位清单（含 name/desc 展示文案）仍是一份独立硬编码；将来加档位（如 hires）会漏。UI 行禁用判定 `availableQualities.indexOf(opt.key)` 也依赖这份清单。
- 建议：qualityOptions 的 key 数组从 QUALITY_LEVELS 派生（map 出展示元数据），保底 `default` 分支已有。

### H-20｜P3｜requestInStream 非 200 一律当失败，未处理 206/重定向类 CDN 行为
- 位置：OfflineCache.ets ensureDownload 尾部 `const code = await session.requestInStream(...); if (code !== 200) { settle(false); }`。
- 说明：部分 CDN 对带 Range/Referer 的请求回 206；当前会把下载成功判成失败并删 .part。现状（不带 Range 的普通 GET）多半恒 200，属防御性问题。
- 建议：放宽为 `code !== 200 && code !== 206`，或记录实际码进日志辅助排查。

### H-21｜P3｜dataReceive 每块 writeSync 在主线程同步写盘
- 位置：OfflineCache.ets `session.on('dataReceive', ...)`。
- 说明：快 CDN 下回调频率高，同步写可能造成掉帧。洛雪式实现同样如此，属已知取舍；建议后续观察真机表现再决定是否换写队列。

### 存量未修（沿清单编号，不另立）

- **H-10（P3，未修复）**：4 个 quality_*.svg 仍含硬编码 `fill="#A7AAAE"` / `fill="#6C7485"`（grep 实证），代码侧 `.fillColor(...)` 对 SVG 内置 fill 的覆盖行为仍未验证（规格 8.3 要求金色常亮、doc1 §三.1 同）。建议把 svg 内 fill 统一改 white/currentColor 类可染色写法，或真机确认 fillColor 覆盖生效。
- **H-13（部分修复）**：见 H-19。

## 4. KugouVerify 通知与浏览器跳转链路核对

链路完整且防线合理：
1. 消费点：refreshSourceLabel（:1060）与 resolveDirect（:1104-1106）都过 `KugouVerify.consume(r)`，只认 reason==='need_verification'（与 Models.ResolveResponse.verifyUrl/eventId 契约一致）。
2. 节流：同 eventId 只提示一次 + 10 分钟窗口（shouldPrompt），连播刷屏问题被压住；`consume` 在两个入口共享节流，注释与实现一致。
3. 通知：Notifier.notifyAction 独占 id 3002，WantAgent 指回本应用 EntryAbility 并把 url 放 want.uri（规避「通知直接拉浏览器需前台」的限制，设计注释交代了理由）；未授权/构建失败退 AppToast，不静默。
4. 跳转：EntryAbility onCreate + onNewWant 双入口 `openVerifyFromWant`（冷/热启动都覆盖），只放行 http(s) uri（防任意 uri 借道）；KugouVerify.openInBrowser 先锁华为浏览器 bundleName、失败退隐式 browsable Want、再失败提示手动访问。
5. 拼址：absoluteUrl 用 APIClient 当前 baseUrl，归一首尾斜杠，服务端给绝对地址直接用。

小注（不计缺陷）：Notifier.buildAgent 返回类型故意留空是绕 @kit.AbilityKit 未导出 `WantAgent` 名字的已知坑，注释已交代；notifyAction 的 url 参数若为空串会退化成纯文本通知并占用 3001，调用方恒传非空，无实际影响。

## 6. 「做对了」清单

1. **H-1 修得比我建议的更彻底**：不只 await 后复检，连 setMediaSource 失败回退写 p.url 前也复检（:1009），且看门狗回调自带 seq 校验（:1029），超时定时器也不会跨代误杀。
2. **H-2 严格按最终裁定落地**：不取折中（既没报实际档位也没报设备上限），`K_CURRENT_QUALITY` 连同 AppStorage 键一起删干净，UI 两处同源，杜绝再次分叉。
3. **缓存终止语义成体系**：切歌/暂停（待发）/停止/播完/失败落定五条路径都汇到 abortCacheDownload，settle 幂等守卫（settled 标志）保证 destroy/unlink 只走一次。
4. **touchAccess 的三处平台差异踩点准确**：无 Sync 后缀、两参、毫秒——注释把「传秒会被 1970 反向淘汰」的推理写清，且节流避免高频 utimes IO；utimes 失败不记账节流，允许重试。
5. **配额淘汰保护在播文件**：protectedId 跳过 + 超额记 warn 的取舍（宁可超额不断播）方向正确，注释交代了理由。
6. **缓存的「直链可能拿不到」路径**：宁可本轮不缓存也不退回 /api/stream 作下载源（:730-732），规格 4.2 的红线守住了。
7. **normalizeQuality 归一为 lossless 而非丢弃**：脏值不静默降级为 standard，与「默认最高偏好」的产品语义一致。
8. **酷狗验证链路的降级链完整**：通知→toast→手动复制地址，每一级失败都有出口，没有静默吞。
9. **EntryAbility 只放行 http(s) uri**：避免了「任何 want 带个 file:// 就被拉浏览器」的注入面。
10. **refreshSourceLabel 火后不管但带曲目 id 校验**（:1062-1064、:1072-1074），迟到的解析不会污染新曲的音源行。
