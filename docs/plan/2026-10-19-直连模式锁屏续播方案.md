# 直连模式锁屏续播：待决策（2026-10-19）

> 状态：**待用户拍板，暂不实施**。背景见
> `docs/memory/2026-10-19-iOS直连播放链路与锁屏上限.md`。

## 问题

直连模式（App 未配置服务端）下，音源解析在 WKWebView 的 JS 里完成。
锁屏后 JS 被系统挂起，原生虽然还在后台音频模式运行，但没有解析能力，
只能播放「已经拿到 URL」的曲目。

因此：**锁屏连续播放上限 = 已解析并注册直链的曲目数**。预取多少首就只能撑多久，
队列最终一定会用完。这不是实现缺陷，是「解析位置」决定的。

## 三个选项

### A. 预取整队，接受上限

- Web 在开始播放后，对后续若干首调 `resolveDirect(track)`（服务端 `resolveBatch` 的上限是 10 首），
  拿到绝对地址后 `SuenAudio.setDirectUrl`。
- 原生新增 `appendDirect(id)`：该曲目已有直链且不在队列里时 `player.insert` 到队尾，
  **不 `removeAllItems`、不动当前 item**。
- 收益：锁屏能连播约 30–40 分钟；改动集中在 Web + 一个原生的追加方法。
- 代价：到此为止就停；回前台后才能继续补。

### B. 把解析搬到原生（Swift）

- 在 `SuenAudio` 内重写 B 站搜索、`wbi` 签名、网易云取流。
- 收益：真正无限接续，与服务端模式行为一致。
- 代价：工作量大；第三方签名/风控规则一改就得跟版本，维护成本高。**不建议**。

### C. 保留服务端（哪怕只是一个轻代理）

- App 继续配置 `baseUrl`；原生在需要下一首时直接请求 `/api/stream/<id>`。
- 收益：唯一能做到长时间锁屏不断的方式；Web 层不需要直连分支；这也是原应用的工作方式。
- 代价：需要一处可访问的服务端（拆成独立仓库、独立部署都可以）。
- 注意：拆仓 ≠ 不要服务端。决定体验的是「运行时有没有 baseUrl」。

## 待确认

1. 直连是**主路径**还是**无服务端时的降级**？
2. 若是降级：锁屏 30–40 分钟的上限是否可接受（选 A）？
3. 若不可接受：是否恢复「App 必须配置服务端」（选 C）？服务端拆仓后由谁部署、地址如何下发？
4. 选 A 时，预取几首合适？（受 B 站风控限制，串行解析，建议 5–10 首）

## 不在本方案内

- 原生 `skipToNext` / 自动接续在直连下的返回值语义（选中方案后一起定）。
- iOS 桌面卡片：已下线，不再投入（见记忆文档第六节）。
