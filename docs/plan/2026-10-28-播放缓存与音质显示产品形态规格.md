# 播放缓存与音质显示 · 产品形态规格

> 状态：**已定稿**（2026-10-28 用户逐条裁定）
> 本文是后续实现的唯一依据。与既有文档冲突时，**以本文为准**。
> 适用范围：iOS 端、鸿蒙端（服务端不承担缓存流量）

---

## 0. 这份规格解决什么问题

播放走 CDN 直链（不经服务端中转），同时把正在听的这首完整落到本地；下次播放先看本地。
音质显示与缓存解耦：界面显示「本设备能用的最高档」，不显示实际播放档位。

---

## 1. 目标

| 编号 | 规则 |
| :-- | :-- |
| 1.1 | 只缓存**当前正在播的那一首**。不预取后续曲目。 |
| 1.2 | 不缓存「听过但没播到」的歌，不缓存队列里的其他歌。 |

> 明确不做：Amperfy 式的「预取后三首」。理由：用户是否继续听、是否听完就关，无从判断，预取大概率白下。

---

## 2. 触发

| 编号 | 规则 |
| :-- | :-- |
| 2.1 | **起播后 25 秒**才发起缓存下载。 |
| 2.2 | 启动前**不做任何播放状态检查**：不做卡顿检测、不做带宽让路判据。 |
| 2.3 | 一旦启动，**一口气下完**；中途不暂停、不让路、不降速。 |

> 25 秒门槛的作用是「试听过滤」：不喜欢的歌在 25 秒内切走，一个字节都不下。
> 不做状态判据的前提是：一旦开下就不需要再让路，因此持续观察播放状态没有意义。

---

## 3. 终止

| 编号 | 规则 |
| :-- | :-- |
| 3.1 | **切歌或播完，立即取消**未完成的下载。 |
| 3.2 | 已下载的部分**直接丢弃**，不保留 .part、不续传。 |
| 3.3 | 取消后不留任何残余状态；下次起播重新从头判断。 |

> 取舍（用户已确认接受）：慢网用户的长歌可能**永远缓存不成** —— 每次都不够时间下完，且不留残片。

---

## 4. 下载源

| 编号 | 规则 |
| :-- | :-- |
| 4.1 | 下载源**只能是当前曲的 CDN 直链**，并带上直链所需的请求头。 |
| 4.2 | **绝不**用 /api/stream 代理地址作为下载源。 |
| 4.3 | 服务端**不再为缓存承担任何带宽**。 |
| 4.4 | **播放侧仍保留 `/api/stream` 作为兜底**（直链解析失败时回退）。本表 4.1/4.2 的「只用直链」约束**仅针对缓存下载源**，不约束播放通道。web 端以 `/api/stream` 为主通道（浏览器 `<audio src>` 无法携带自定义 Referer，直链必然 403），服务端路由与 `session-token` 因此保留。 |

---

## 5. 完整性判定

| 编号 | 规则 |
| :-- | :-- |
| 5.1 | 有 Content-Length：**收到的字节数必须等于它**，差一个字节都不算完整。 |
| 5.2 | 没有 Content-Length（分块传输等）：**以流正常结束**作为完整。 |
| 5.3 | 判定不完整 → 丢弃，不留残余、不写缓存索引。 |
| 5.4 | 完整性只与「字节是否齐全」有关，**与收听进度、是否拖动、是否播到结尾完全无关**。 |

---

## 6. 存储

| 编号 | 规则 |
| :-- | :-- |
| 6.1 | 落在**持久目录**，不落系统会自动回收的临时缓存目录。 |
| 6.2 | 配额 **1GB**（2026-10-28 下午由 2GB 下调，UI 上显示为 `1G`）。 |
| 6.3 | 超过配额：按**最久未使用优先覆盖/删除**。 |
| 6.4 | 缓存文件名与索引**不包含音质信息**，一首歌一份。 |

> 1GB 的量级参考：最高音质单曲约 10MB 级，可容纳 100 首以上。

---

## 7. 命中行为

| 编号 | 规则 |
| :-- | :-- |
| 7.1 | 本地有该曲缓存 → **直接播本地，不再回上游取流**。 |
| 7.2 | 缓存与音质解耦：缓存的是「当时下到的那一份」，不因用户改偏好而失效。 |
| 7.3 | 已知后果（用户已确认）：弱网下缓存的歌会被**永久锁在当时的档位**，用户不可见。 |

---

## 8. UI

| 编号 | 规则 |
| :-- | :-- |
| 8.1 | **不显示缓存进度**：播放页进度条上不出现灰色缓存段。 |
| 8.2 | 缓存 UI = **设置页里的一行**：左侧「缓存」、右侧显示真实占用，格式形如 `100M / 1G`（已用不足 1G 时用 M，上限写 `1G`）；点该行弹**确认框**「是否清空缓存」，确认后清空并刷新。**不做缓存列表页**，不列曲目、不做单条删除（对齐 web `OfflineCachePanel` 的「只显示占用、让用户显式清空」）。 |
| 8.3 | 音质显示 = **用户选择的档位**。播放页七键的音质按钮与音质面板的「当前生效」**都取这一档**，两处同源。 |
| 8.4 | **不显示实际播放档位**：服务端可能降档下发，界面不随之变化。**不再有「设备能力上限」这套口径。** |

> ⚠️ 8.3/8.4 的口径一共变过两次，最终以此为准：
> ① 最初「如实显示实际播放档位」→ ② 改成「显示设备能力上限」→ ③ 最终「显示用户选择的档位」。
> 变更原因：②会让「当前生效」与面板里带 ✓ 的偏好项自相矛盾；③让两处一致，且用户看到的就是自己选的。

---

## 9. 已知取舍汇总

1. 慢网长歌可能永远缓存不成（3.2 + 3.1）。
2. 缓存档位被永久锁定，且界面不反映（7.3 + 8.4）。
3. 缓存下载与播放使用同一条网络，弱网下两者会互相挤压（2.2 不做让路）。
4. 服务端省下了缓存带宽，但每首歌听 25 秒后会多一次 CDN 下载（同源不同连接）。

## 12. 参考：行业内三家真实实现（2026-10 调研）

| | Cassette（iOS） | Amperfy（iOS） | 洛雪音乐鸿蒙移植版 |
| :-- | :-- | :-- | :-- |
| 拦截字节 | 无 | 无 | 无 |
| 缓存对象 | 当前曲 | 后 3 首 | 当前曲 |
| 起下时机 | 播满 30 秒 | 起播即预取 | 起播即入队 |
| 让路 | 无 | 无 | 分块 + 让路判据 |
| 半截数据 | 丢弃 | — | 保留 .part 续传 |
| 超配额 | FIFO 最近 10 首 | 停止下载 | 512MB LRU |
| 完整性 | 磁盘大小 == 记录大小 | isCached 标记 | .part 改名 |

**没有一家做字节拦截**；鸿蒙 AVPlayer 不提供流式字节回调（洛雪源码注释明确写了这一点），华为 dataSrc 在生产代码中零先例。

本文的设计 = 洛雪式的「当前曲 + 不用分块」，加上 Cassette 式的「起下延迟」，再按我们的令牌时效约束去掉续传。
