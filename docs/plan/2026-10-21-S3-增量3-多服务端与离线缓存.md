## 一、为什么这两个放在最后（风险最高）

| 风险 | 具体后果 |
|---|---|
| **切服会让整条播放队列失效** | 原生队列里存的是**绝对 URL**（`http://<base>/api/stream/<id>?t=<token>`）。base 一变，队列里每一条都 404/401 → 从通知栏/锁屏按播放必失败 |
| **切服容易丢播放位置** | Web 端踩过：切服后从 0:00 重听（`pendingSeekMs` 被后续 `startLoad` 清空）。原生端同样会踩 |
| **缓存文件可能被删时正在播放** | `fd://` 播放期间删文件 → 播放直接中断，且错误码难懂 |
| **切服失败必须回滚** | 否则用户停在"半切换"状态：地址变了但鉴权是旧的，每个请求都 401 |

## 二、要新增的能力（现有 API 不够，按此补）

### 2.1 `core/OfflineCache.ets`（现有：`init/isCached/cachedPath/ensureDownload`）

```ts
/** 单条缓存信息 */
export interface CacheEntryInfo {
  trackId: string;
  path: string;
  bytes: number;
  /** 毫秒时间戳（文件 mtime） */
  savedAt: number;
}

/** 列出全部已完整缓存的曲目（按 savedAt 倒序） */
listEntries(): CacheEntryInfo[];

/** 已用字节数 */
usedBytes(): number;

/** 配额（2GB 常量，UI 要显示） */
quotaBytes(): number;

/** 删除单条缓存。返回 false = 文件正被播放占用或删除失败 */
remove(trackId: string): boolean;

/** 清空全部缓存。返回实际删除条数 */
clearAll(): number;

/** 重新扫盘（外部改了文件后刷新索引） */
rescan(): void;
```

**实现要点**
- 目录仍是 `context.filesDir + '/audio_cache'`，**禁止改到 `cacheDir`**（系统会按配额自动清理）
- `remove` / `clearAll` 必须跳过**当前正在播放**的曲目：由调用方传入 `playingTrackId`，
  或用 `OfflineCache.setProtected(trackId)` 由播放内核在 `playing` 时登记、切歌时清除
- 删完要 `enforceQuota()` 之外再刷新 `complete` 索引，避免 `isCached` 还返回 true

### 2.2 `core/APIClient.ets`（现有：`init/getBaseUrl/getServers/isLoggedIn/setServers/adopt/signOut` + 各业务方法）

```ts
/** 探测单个服务端：健康检查 + 校验返回体 ok 字段（门户劫持也会回 200） */
async probeServer(url: string): Promise<boolean>;

/** 并行探测全部候选，返回 url → 可达 */
async probeAll(): Promise<Record<string, boolean>>;

/**
 * 切换当前服务端。
 * 顺序：探测 → 临时切过去 → `me()` 验证鉴权 → 成功则持久化；失败则**回滚**到原地址并抛出原因。
 * 返回 true = 已切换（调用方随后需要 rebind 播放队列）
 */
async switchServer(url: string): Promise<boolean>;
```

**实现要点**
- 归一化 URL（去尾斜杠）、拒绝空串
- `switchServer` 内部必须保存原 `baseUrl`，任何一步失败都恢复它
- 切换成功后**清空** `accessToken`（新服务器不接受旧令牌），但保留 `refreshToken` 让对方 401 一次再刷新；
  若 `me()` 直接 401，再尝试一次 `refresh()`，仍失败则抛出"该服务器上你的账号需要重新登录"
- 不要在这里改 `servers` 数组顺序（由 UI 决定）

### 2.3 `core/MediaPlayerCore.ets`（只加方法，不动既有状态机）

```ts
/**
 * 换服后重建播放队列：保住「当前曲目 + 播放位置 + 播放意图」。
 * 步骤：记下 index/positionMs/wantPlay → 用新 base 取流令牌（失败降级空令牌）
 *      → setQueue(同一队列, 同 index, 新 token) → seek(positionMs) → 若原在播则 play()
 */
async rebindServer(token: string): Promise<void>;

/** 当前播放位置（毫秒），给 rebind 与 UI 用 */
get positionMs(): number;
```

**⚠️ 这是本增量最容易做错的地方**：不能只改 `APIClient.baseUrl` 就完事，
必须走 `setQueue` 重建（队列里存的是绝对 URL）。

## 四、四条硬约束（违反即打回）

1. **切服必须保住播放位置**：验收时会盯着时间戳 —— 切服前后 `positionMs` 差必须 < 3 秒。
   禁止只改 baseUrl 不重建队列。
2. **切服失败必须回滚**：地址恢复原值、令牌状态不变、给用户明确原因（不可达 / 该服务器无此账号 / 鉴权失败）。
3. **缓存只落 `filesDir`**，且**删除时跳过正在播放的曲目**（`fd://` 占用中）。删除失败要提示"正在播放，已跳过"。
4. **清空缓存要二次确认**，并显示将释放多少 MB。

## 五、验收 8 条（缺一不算过）

| # | 操作 | 判定 |
|---|---|---|
| 1 | 服务端管理页打开 | 列出全部候选，每个都带可达/不可达状态（同网段应全绿） |
| 2 | 新增一个错误地址（如 `http://192.168.1.99:3210`） | 保存后状态显示不可达；不影响当前正在用的服务端 |
| 3 | 播放中切换到另一个可用服务端 | 出声不断，**位置从切前的时刻继续**（差 < 3 秒）；锁屏信息仍是同一首 |
| 4 | 切换到一个不可达地址 | 明确报错 + **地址回滚**到原值；播放不受影响 |
| 5 | 删除当前正在用的服务端 | 自动切到剩余第一个（或提示无可用服务端）；播放按 §四.1 处理 |
| 6 | 缓存面板 | 已用/配额正确（与文件管理器里 `filesDir/audio_cache` 总大小一致）；条目数与 `K` 缓存曲数一致 |
| 7 | 删除单条缓存（非当前曲） | 条目消失、用量下降、该曲之后再播会重新走网络并重新落缓存 |
| 8 | 删除**正在播放**那首的缓存 | 拒绝并提示"正在播放，已跳过"；播放不中断 |

## 六、高风险点（提前标）

| 点 | 说明 |
|---|---|
| `rebindServer` 与 `failHandled`/`failStreak` | 重建队列时要把这两个计数清零，否则一次失败会被记进新服务器的账 |
| `setQueue` 会 `bumpQueue()` | 重建后 `K_QUEUE_VERSION` 变化是**预期**的，队列页会重取快照，不用特殊处理 |
| `seek` 要在 `prepared` 之后 | 沿用现有做法：`stateChange('prepared')` 里按 `pendingAutoplay` 处理；位置恢复建议记 `pendingSeekMs`，在 `prepared` 里 `seek` 一次 |
| `probeAll` 并发 | 5 个候选并行探测，每个 2 秒超时；UI 用「未知/检测中/可达/不可达」四态，别用布尔红绿灯导致闪烁 |
| `preferences` 写入 | `setServers` 已 `await flush()`，沿用 |
