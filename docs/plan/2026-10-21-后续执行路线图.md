## 四、Lead 的审 bug 口径（每次回执我都按这六条查）

| # | 检查 | 不通过的样子 |
|---|---|---|
| 1 | **静态自检** `npm run hw:check`（0 ERROR / 0 WARN） | 有 ERROR 直接打回，不进入人工审 |
| 2 | **三条硬约束是否被破**：`audioRendererInfo` 只在 `initialized`；`failStreak/MAX_FAIL_STREAK`；AVSession 闸门（`statePushInFlight` + `currentMetadata !== null` 去重） | 为"过编译"或"更及时"把这些挪位/去掉 |
| 3 | **契约对齐**：请求路径/参数/字段与服务端源码一致（`hasMore` 分片、`shortfall` 非错误、`GET /api/recommend/daily` 只读） | 自己发明字段或把"空"当"错" |
| 4 | **改动范围**：只落在 §三 允许的文件里 | 顺手重构、动了服务端或 iOS |
| 5 | **日志自洽**：回执里的现象与 hilog 是否互相印证 | "验收 ✔"但日志里没有任何对应行 |
| 6 | **交互自洽**：队列/下标/令牌/缓存穿越场景（切服、删当前曲、删在播缓存） | 高亮跟着序号而不是跟着歌 |

### Bug 单格式（我会按这个给，方便直接转交）

```
[BUG-n] P0|P1|P2
文件:行
现象：<用户可见的现象>
根因：<代码层的原因，指向具体语句>
修法：<最小改动建议>
复现：<步骤>
```

- **P0**：崩溃/白屏/播不出声/丢数据
- **P1**：主流程可见缺陷（切服丢位置、锁屏失效、跳过逻辑错）
- **P2**：体验瑕疵（文案、对齐、动效）
