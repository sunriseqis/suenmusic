# 终止客户端直连，回归服务端单一真相源与原生磁盘缓存（2026-10-20）

> **归档背景**：针对 10/17 ~ 10/19「客户端直连音源 + 本地优先 IndexedDB」实验的深度复盘与终结结论。  
> **状态**：已拍板并落地执行。

---

## 一、为什么客户端直连在工程上必须被终止？

1. **iOS 系统的物理限制（无法逾越）**：
   - 锁屏或退至后台约 5~15 秒后，系统无条件挂起 WKWebView 内的 JS 引擎；
   - B 站 WBI 签名加密与流解析跑在前端 JS 里，锁屏后直接失去解析能力；
   - 原生 `AVQueuePlayer` 无法获取后续直链，队列只有 1 首歌，曲末停播导致系统立即吊销后台音频权限，进程被冻结/杀掉；
   - 试图在原生切歌时调回 Web 解析，引发了 30ms 一次的队列重建死循环。
2. **预装填（Prefetch Window）的硬上限**：
   - B 站反爬对高频并发搜索与取流具有严格突发风控（频繁 -412）；
   - 端侧预填安全窗口最多 5~10 首（约 30~40 分钟），用完即硬中断，无法像其他主流播放器一样在锁屏下无限畅听。
3. **数据孤岛与三端撕裂**：
   - 本地优先（IndexedDB）导致收藏、历史、进度与手动锚点（Anchor）变成单机数据；
   - 桌面端锚定的完美版本在移动端完全不生效，跨端体验严重退化。
4. **反爬与防盗链维护黑洞**：
   - 第三方规则（WBI/Cookie）微调需要全量重新发版、打包自签 IPA/APK，维护成本失控。

---

## 二、真正的全端一致性架构

回归以**服务端为单一真相源（Single Source of Truth）**，移动端与 Web 端享有统一的数据与音频通道：

1. **数据全同步**：
   - 收藏、歌单、历史、进度、音源锚定（`anchors`）统一存储于服务端 SQLite，三端实时对齐，无单机孤岛；
   - 离线时客户端仅使用轻量只读快照兜底渲染，重连后向服务端对齐。
2. **流代理收敛**：
   - 音源的 WBI 签名、Cookie 轮换、403 自愈、Range 206 续拉全部收敛在服务端的 `/api/stream/:id`；
   - 端侧原生播放器（iOS `AVQueuePlayer` / Android `Media3`）只需持有统一的标准流地址，锁屏时由系统网络层向服务端拉取，**彻底实现后台无限切歌**。
3. **弱网抗抖动依靠本地磁盘缓存，而非直连**：
   - iOS 端的 `SuenAudioCache.swift` 作为本地回环代理（127.0.0.1）边播边把流存入磁盘（4GB LRU）；
   - 弱网、断网、切网（Wi-Fi ↔ 蜂窝）时，本地代理始终以 `206 Partial Content` 毫秒级输出已缓存字节，**播放器时间轴绝不重置归零，杜绝从头开始与静音空转**。
