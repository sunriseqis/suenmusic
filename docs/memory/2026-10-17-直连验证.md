# 无后端直连：真机验证结论（2026-10-17）

**结论：三端可以脱离自建后端直接使用。三个问题全部在真机上验证通过。**

验证方式：`output/test/SuenMusic-android-debug.apk` 里的诊断页（`/probe`），
真机、移动网络、**零登录凭据**。第二轮全绿。

```
✅ 取 buvid3 / buvid4              游客设备标识，不需要登录
✅ QQ音乐 搜索（元数据）            命中 5 首
✅ B站 搜索（search/all/v2）       有候选
✅ 本地存储读写                    IndexedDB 写入并读回
✅ 解析音频地址                    playurl 拿到音轨
✅ 音频 CDN Referer 校验           带 Referer 可播
✅ 原生播放器播放直连地址           出声
```

## 一、必须走原生请求：WebView 会自动带 `Origin`，而 B站拒绝它

**第一轮真机全灭（5 种请求头组合全是 412，返回体一字不差）。**
根因有两条，**主因是第二条**：

**① `fetch` 会静默丢弃禁止头**

`Origin` / `Referer` / `Cookie` 是 fetch 规范的**禁止头**（forbidden header
names），`fetch()` 丢它们**不报错、不警告**：

```js
// ❌ 这三个头一个都发不出去
fetch(url, { headers: { 'User-Agent': UA, Referer: '...', Cookie: 'buvid3=...' } });
```

**② WebView 发的请求自带 `Origin: http://localhost`，且无法覆盖**

这才是致命的那条。实测对照（均为"仅 UA"）：

```
真机 fetch（WebView，自动带 Origin: http://localhost） → 412
真机 CapacitorHttp（原生，不带 Origin）                → 200
```

沙箱侧同向印证：`UA + Origin(b站)` → 200，`UA + Origin(任意第三方域)` → 412。
**B站对非 bilibili 的 Origin 一律拒绝**，而 WebView 里这个头改不了、去不掉。

→ 所以元数据请求**必须走原生**：不是为了能设 Referer/Cookie（那两条其实不必要），
而是为了**不发 Origin**。

**踩坑时的诊断要点**：如果多个请求头组合得到**完全相同的响应体**，
说明请求头不是变量 —— 要么没发出去，要么决定性因素是请求本身而非头。

**正确做法**：原生环境直接调 `CapacitorHttp.request()`。

```js
// ✅ 插件 API 路径，headers 由原生发送，且不会自动附加 Origin
import { Capacitor, CapacitorHttp } from '@capacitor/core';
const res = await CapacitorHttp.request({ url, method: 'GET', headers: { 'User-Agent': UA } });
// 返回 { status, data(已解析), headers, url } —— data 不需要 .json()
```

补丁能不能生效**别靠猜**：诊断页会把实际通道打出来
（`CapacitorHttp（原生，可发禁止头）` vs `fetch（浏览器，禁止头会被丢弃）`）。

已核实的两点（不要凭印象）：
- `@capacitor/android/.../plugin/util/CapacitorHttpUrlConnection.java:setRequestHeaders`
  把每个头原样 `setRequestProperty`，**不做任何过滤**
- `Bridge.java:663` 在 `registerAllPlugins()` 里**无条件注册** `CapacitorHttp`
  —— 它是核心插件，**不经过 `capacitor.plugins.json`**（那个文件对核心插件一直是 `[]`，
  看到空数组不要以为没注册）

⚠️ `capacitor.config.ts` 里开 `plugins.CapacitorHttp.enabled` **只影响
`fetch`/`XMLHttpRequest` 的补丁**；补丁没生效时不报错。要可靠就直接调插件 API。

## 二、B站：游客能拿到什么

**凭据分两层，别混为一谈（混了会得出"必须登录才能播"的错误结论）：**

| 凭据 | 性质 | 怎么拿 | 作用 |
|---|---|---|---|
| `buvid3` / `buvid4` | **游客设备标识** | `GET /x/frontend/finger/spi`，**无需登录** | 过反爬 |
| `SESSDATA` | 登录凭据 | 扫码登录 | **只影响音质档位**，不是播放前提 |

**真机结论：搜索"仅 UA"就够** —— 三种组合（仅 UA / +Cookie / +Referer+Cookie）
全部 200、各 20 个候选。

> ⚠️ 别把沙箱测的"仅 UA → 412"当结论：那次走了新加坡 Cloudflare 代理
> （AS13335），**是 IP 级风控**，不是请求头问题。**这类上游测试必须在家宽出口做。**

**端点用 `search/all/v2`**（服务端一直用的就是它）：

```
✅ /x/web-interface/search/all/v2?keyword=...     20 个视频候选
❌ /x/web-interface/search/type?search_type=video  0 候选
```

**搜索必须限流**：服务端专门做了 400ms 串行间隔，注释写着「B站搜索敏感，
并发突发会触发 -412 风控」。客户端照做（实测用 500ms）。

---
服务端一直用的是前者，直接照抄它。响应是**分段结构**：

```ts
// data.result[] 里每段带 result_type，视频在 'video' 那段
for (const sec of json?.data?.result ?? []) {
  if (sec?.result_type === 'video') return sec.data ?? [];
}
```

**搜索必须限流**：服务端专门做了 400ms 串行间隔，注释写着「B站搜索敏感，
并发突发会触发 -412 风控」。客户端照做（实测用 500ms）。

**音频 CDN 是否校验 Referer —— 结论是"看节点"，不能一概而论：**

```
沙箱（cn-sccd-ct-02-13.bilivideo.com）  带 Referer → 206 ；不带 → 403
真机（xy...mcdn.bilivideo.com:8082）    带 / 不带 / 全不带 → 三个都是 206
```

两次样本**结论相反**，说明校验与否取决于具体 CDN 节点（`mcdn` 是移动/P2P 节点，
比电信节点宽松）。真机那轮是**单个样本，不能推广**。

→ **正确做法：原生播放器照旧带上 `Referer`。** 带了在宽松节点上无害，
在严格节点上是必需的；不带的代价是"某些节点整首歌都放不了"。
（Android 在 `SuenAudioCache` 的 http 数据源上设默认头即可。）

**不要因为样本一次通过就删掉这类防御** —— 这是本轮最容易犯的错，
我自己就先写下了"不需要 Referer"的错误结论。

## 三、QQ音乐：元数据主力，零凭据

`u.y.qq.com/cgi-bin/musicu.fcg` 的 `DoSearchForQQMusicDesktop`，**不带任何凭据**
即可用，只要 UA + `Referer: https://y.qq.com/`。

`req.code === 2001` 表示**风控冷却**，不是参数错误 —— 服务端有 `qqCooldown`
处理这个码，客户端也要认。

## 四、原生侧的硬拦截（脱离后端的第一处卡死）

`android/.../SuenAudioService.java` 原先：

```java
if (SuenAudio.getBaseUrl() == null || SuenAudio.getSessionToken() == null) {
  return Futures.immediateFailedFuture(new IllegalStateException("尚未配置服务器地址或流会话令牌"));
}
```

**没配服务器地址就直接抛异常** —— 这是"脱离后端"在原生侧最先卡住的地方。
改法是加"直连例外"：整队条目都有 `directUrl` 时放行。
