## 一、逐条改动

### A-1　iOS 不可构建：删掉 pbxproj 的 8 行悬空引用

`ios/App/App.xcodeproj/project.pbxproj` 里 `SharedNowPlaying.swift`、`PlaybackIntents.swift` 各有 4 处残留（PBXBuildFile ×2、PBXFileReference ×2、group children ×2、Sources 阶段 ×2）。文件早在「iOS 卡片整体移除」那轮随目录删掉了，工程引用没跟着删。

改法：精确删这 8 行（不是整段重排，避免 objectVersion 与顺序被打乱）。

自检（无 macOS，用结构等价校验替代 `xcodebuild`）：
- 4 个 object id（`…A4/A5/B4/B5`）在全文件残留 **0** 处 —— 无悬空引用、无重复定义；
- 花括号 `54/54`、圆括号 `26/26` 平衡；
- 行数 424 → 416，diff 只有 8 行删除。

**教训**：`docs/memory/2026-10-20-iOS卡片移除与工程收尾.md` 当年写的是「pbxproj 零悬空」，与事实相反。删除 target 的收尾清单里必须包含「grep 文件 basename 在 pbxproj 里的残留」。

### A-2　鸿蒙被判成同源 Web 面板 → 整端连不上服务端

根因不是「判定写错」，而是**判定分散在两处各写一套**：`api/client.ts` 只看 `Capacitor.isNativePlatform()`，`native/update.ts` 里另有一套 `isHarmony`。鸿蒙不走 Capacitor，于是 client 侧把它当浏览器。

改法（收敛为单一来源，而非就地打补丁）：
1. 新建 `web/src/native/platform.ts`：`isHarmony`（看 `window.SuenHarmony` 注入）、`isCapacitorNative`、`isNativeShell`（= 两者之并）、`isWebPanel`（= `!isNativeShell`）。
2. `api/client.ts` 三处判定全部改用 `isNativeShell`：`isWebPlatform`、`hasBackend()`、`rawFetch` 里的 `web`（决定 `credentials` 与 `X-Requested-With`）。同时删掉不再需要的 `@capacitor/core` 直接依赖。
3. `native/update.ts` 删掉自己那份定义，改为 `export { isHarmony, isNativeShell, isWebPanel } from './platform.ts'`，所有既有 import 路径不用改。
4. `views/Settings.vue` 的「多服务端」门禁从 `isNativeAudio` 换成 `isNativeShell` —— 鸿蒙没有 Capacitor 音频插件，用 `isNativeAudio` 当门禁等于永远不给它改地址的入口。

连锁恢复（同一条根因，一并治好）：登录页地址框（`Login.vue:90` 的 `!isWebPlatform`）、`buildUrl` 不再拼相对路径、`session.ts` 五个 `isWebPlatform` 分支在鸿蒙上一律走 Bearer（与 Android/iOS 同一路径，不再尝试注定失败的跨源 cookie 会话）。

**教训**：平台判定是「跨端契约」，必须单一来源。任何 `Capacitor.isNativePlatform()` 的直接调用点都是潜在漏判。

### A-3　`hw/hvigorw` 缺执行位

git 索引里是 `100644`，而 `scripts/build-hw.mjs` 用 `execFileSync(join(HW_DIR,'hvigorw'))` 直接调用 → 干净 clone 上必然 `EACCES`（实测 `bash: ./hvigorw: Permission denied`）。

改法：`git update-index --chmod=+x hw/hvigorw`（现为 `100755`）+ 脚本里调用前 `chmod 0o755` 兜底（Windows/WSL 复制会丢权限位），并在文件缺失时给明确报错而不是一句 `Permission denied`。

验证：`./hw/hvigorw --version` 不再 Permission denied；现在走到脚本自身最后那支 `npx @ohos/hvigor-cli`，404 属「本机没装 hvigor」的既有情形（该分支的注释里早已写明）。

### A-4　B 站搜索路径缺 `source` 字段 → `npm test` 常红

`resolveTrackSource()` 的**搜索路径**返回对象缺 `source: 'bilibili'`（锚点路径一直有），于是 `resolveTrack()` 交出的 `source` 是 `undefined`，`resolver-test` 的「多源解析命中有效源」永远失败（62 通过 / 1 失败）。

改法：
1. `server/src/sources/bilibili/stream.ts` 搜索路径补 `source: 'bilibili'`；
2. `services/resolver.ts` 的锚点沉淀条件 `(result.source ?? 'bilibili') === 'bilibili'` → `=== 'bilibili'`（两条上游路径现在都显式带值，兜底多余，且正是它把「字段漏了」掩盖成「只有测试知道」）；
3. `web/src/api/types.ts` 的 `ResolveResponse.source` 由可选改**必填**，`player.ts` 相应去掉 `?? 'bilibili'`。

**口径修正（与计划原文有出入，已回写计划）**：计划里写的是「清掉两处 `?? 'bilibili'`」。实测发现不能只删兜底 —— 删了兜底就必须同时把「服务端保证非空」写进类型，否则 `currentSource.value = result.source` 直接类型报错；而服务端 `routes/resolve.ts` 本来就有 `row?.source ?? outcome.source ?? 'bilibili'` 的归一化，所以把这个保证提到 wire 契约上是成立的。**兜底不是不能删，而是要连类型一起收紧，把「静默错标」变成「编译期不可能」。**
