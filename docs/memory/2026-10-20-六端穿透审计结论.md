## 二、两条 P0（装不上 / 用不了）

### P0-1 iOS 当前不可构建

`project.pbxproj` 里 `SharedNowPlaying.swift`、`PlaybackIntents.swift` 各 4 处残留（:21-22、:45-46、:83-84、:188-189），而 `ios/App/App/` 下只剩 5 个 swift 文件，全仓搜不到这两个名字。`xcodebuild` 会报 `Build input file cannot be found`。

**推翻一条旧记忆**：`docs/memory/2026-10-20-iOS卡片移除与工程收尾.md` 写的「pbxproj 零悬空」与事实相反。教训 —— 「文档宣称已清理」不能替代 `grep`。

### P0-2 鸿蒙壳连不上服务端

`web/src/api/client.ts:106` 用 `!Capacitor.isNativePlatform()` 当「浏览器」判据，但鸿蒙**没有 Capacitor**（`native/update.ts:7-9` 自己写明，并留了 `isHarmony`）。于是鸿蒙被当成「同源 Web 面板」，四处连锁失效：登录页地址框不渲染（`Login.vue:88`）、设置页多服务端区块不渲染（`Settings.vue:600`）、`buildUrl()` 拼出相对地址打回 `http://localhost`、ArkTS 拦截器把无扩展名的 `/api/**` 回退成 `index.html` 导致 JSON 解析失败（`Index.ets:1169-1175`）、写请求的 `X-Requested-With` 又不在服务端 CORS 白名单。

**一句话**：跨端平台判定的单一来源必须收敛到「Capacitor 原生 ∪ 鸿蒙 bridge」，任何一处漏判都会让整端失联。

## 三、P1 分布（详见计划文件）

- **服务端**：`.sm` 解压无输出上限（任意注册用户可 OOM 单进程）、`trustProxy:true` 使登录节流可绕过、`.env.example` 占位密钥被静默接受。
- **Web**：>500 首的收藏恢复静默变 0 首、快速切歌把新曲音频摘掉、nginx 缺 `client_max_body_size` 导致恢复 413。
- **Android**：RemoteViews 里用裸 `<View>` 使两张卡片真机必失败、`tailOnly` 索引钳制会覆盖正在播的曲目、keystore 入库且口令硬编码。
- **iOS**：`tailOnly` 不同步逻辑队列、`reloadCurrent` 定位错位、来电打断后无声、LRU 跨启动不淘汰。
- **鸿蒙**：`/api/**` 被 SPA 回退、返回键不接 `__suenBack`、`hvigorw` 无执行位。
- **fnOS**：不导出 `SUENMUSIC_JWT_SECRET`（每次重启轮换 → 流令牌失效、播放中断）、升级不停旧进程、无守护、`stop/status` 只认 PID。

## 四、复核后否掉的误报（最值得记住的部分）

1. **「`web/dist` 已入库」→ 假**。`git ls-files web/dist` = 0。子代理把 `.gitignore` 内的构建产物当成已跟踪文件。
2. **「JWT 轮换导致 AES 密文永久解不开」→ 链不成立**（这条最初是 Lead 自己的推测）。`encryptSecret`/`decryptSecret` 全仓**零调用点**，`netease-account.ts:33` 还把 `netease.password_cipher` 列为启动即清的 legacy key。**教训：看到 `secret-box.ts` 有完整实现就假设它在用，是典型的「读代码读出了不存在的数据流」，必须 grep 调用点。**
3. **「内置 Node 22.14 vs `engines >=22.18` 会起不来」→ 实测无问题**。下载 v22.14.0 真二进制跑通（`node:sqlite` 可用）。`engines` 是声明，不是运行时校验。
4. **「Android versionCode 默认 1 会拒更新」→ 降级为流程提示**。`build-ios.mjs:136` 注释表明安卓由 CI 传 `VERSION_CODE`。

另：`docs/memory/2026-10-20-飞牛fnOS套件工程与fpk构建交付.md` 里「内置独立便携 Node.js 22 运行时**与原生进程守护**」也不准确 —— `fn/cmd/main` 只有 `nohup ... &`，无守护无重启（计划 D-3）。

## 五、复核阶段新发现（六个子代理都没报，由实测暴露）

1. **`npm test` 现在常红**：普通搜索路径的 B 站结果**缺 `source: 'bilibili'`** —— `sources/bilibili/stream.ts:469-483` 的对象里没有，而锚点路径 `:406` 有。于是 `resolveTrack()` 返回 `source=undefined`，调用方被迫各写 `?? 'bilibili'` 兜底（`resolver.ts:280`、`player.ts:797`）。测试挂在「多源解析命中有效源 — source=undefined」。**修一行即可，但它卡着整个测试门槛。**
2. **`server/src/vendors/netease/data/china_ip_ranges.txt` 缺失**：`vendors/netease/util/index.js:41` 每次启动 `readFileSync` 它，缺失就 `logger.error` 并退回随机 IP（可能是非中国 IP）。文件既没入库也没被 `build-fn.mjs` 生成 —— **但 `docs/memory/2026-10-20-多代理全仓审计与收敛报告.md` 声称「已补全」**。又一次「记忆宣称已完成、实物不在」。

> 方法论教训（本次最大收获）：**凡「已修复 / 已清理 / 已补全」的结论，一律以 `grep` + 实际启动验证为准，不采信文档自述。** 本次审计里被记忆文件误导的共 3 处（pbxproj、china_ip_ranges、fnOS 守护）。
