# 2026-10-30 · 锚点换源仍放旧音源（iOS）+ B 站候选非录音室版本硬过滤

> **归档类型**：用户真机报障 → 三端对齐修复；含一条"软惩罚不能否决"的算法教训
> 关联：[iOS 换播放内核](2026-10-28-iOS换播放内核决策-libmpv.md)、
> [多源音源改造](2026-10-27-多源音源改造落地与问题清单.md)

## 一、现象（用户真机反馈）

> 「缓存被保存下来之后，如果我想切换锚点，他就会一直停在上一次出错了的缓存上面，
> 就一直播出错的那个缓存。你切换锚点，他也不会去清空这个错误的缓存，所以就导致新的锚点没有办法听。」

- iOS 真机，同一曲目先播过一段时间（已整首落盘缓存）→ 在锚定弹窗换一个明显不同的视频 →
  **听到的还是旧音源**，锚点角标也不变；怎么重试、切走切回来都无效。
- 服务端一侧完全正常：`POST /api/tracks/:id/anchor` 已经 `invalidateTrack`（内存 LRU + `play_sources` 连 `:%` 档位键一起删），
  下一发 `/api/resolve` 必然是新的。

## 二、根因：同一套收尾，web 与鸿蒙都做了，只有 iOS 没做

`AudioEngine.resolveSource` 的取流优先级是 **① 本地整首缓存 → ② 内存直链 `directLinks[id]` → ③ 服务端代理流**，
前两级都只按**曲目 id** 索引，与锚点无关。而 iOS 的 `reloadCurrentTrack` 当时只调了 `engine.reloadCurrent`：

| 换源收尾 | web `retryAfterAnchor` | 鸿蒙 `doAnchor` | iOS（修前） |
| :-- | :-- | :-- | :-- |
| 清本地整首缓存 | `SuenAudio.evictCache({id})` | `OfflineCache.remove(id)` | **无**（`AudioCacheStore.evict` 全工程零调用点 = 死代码） |
| 清内存直链 | —（浏览器无此层） | `retryCurrent` 内 `this.direct = null` | **无**（旧 bvid 的 CDN 地址一直留着） |
| 先取新源再装载 | `load(force:true)` | `loadCurrent` 内先 `await resolveDirect` | **顺序反了**（先重装，异步 `refreshSource` 的返回值到达时已装载完毕） |

三者叠加的结果：换了锚点，`resolveSource` 第 ①/② 级立刻把旧音源喂给 mpv，用户永远听不到新锚点。

## 三、修复（三处 + 解锚路径双端补）

1. `PlaybackService.reloadCurrentTrack` 严格对齐鸿蒙 `doAnchor` 三步，**顺序也一致**：
   `cancelCacheTasks()`（先掐在飞下载）→ `AudioCacheStore.evict(id)` → `engine.setDirect(url: nil)`
   → `await /api/resolve` + `applyResolution`（先落新直链）→ `engine.reloadCurrent`。
   - **顺序为什么不能换**：先 `evict` 再解析，那次在飞下载会在 2-8s 的解析等待里把旧音源字节重新落盘，`evict` 白做。
   - 解析期间用户切歌 → 直接丢弃这批结果，避免覆盖新曲的直链/角标。
2. `AudioEngine.cancelCacheTasks` 从 `private` 放开为模块可见（下载句柄在引擎里，顺序要求"先取消再清"）。
3. **解除锚定**同样等于换音源（回到自动匹配那一版），iOS `AnchorSheet.removeAnchor` 与
   鸿蒙 `PlayerPage.removeCurrentAnchor` 都补上了同一套收尾 + 重装（此前只弹 toast，会继续放旧锚点直到下次切歌）。

## 四、服务端：B 站候选「非录音室版本」硬过滤

用户要求：搜索结果天然过滤 live / 直拍这类非录音室版本。**不是加权重，是过滤**——原因：

> `scoreCandidate` 的 `LIVE_KEYWORDS` 是**扣 20 分**的软惩罚，而一条标题与时长都刚好卡住的直拍：
> 40（时长）+ 25（歌名）+ 15（歌手）− 20 = **60 分，照样过阈值**。扣分只能降排名，不能否决。

实现（`sources/bilibili/matcher.ts`）：

- `isNonStudioTitle(title)`：中文子串（现场/演唱会/音乐节/跨年/直拍/饭拍/舞台/直播/打歌/巡演/返场/歌友会/签售会/彩排/总决赛/晚会），
  拉丁**按词边界**（`\blive\b` / `\bfancam\b` / `\bconcert\b` / `\blivehouse\b`）—— 否则 Alive / Deliver / Lively / Concerted 会被误杀。
- `filterStudioCandidates(trackName, candidates)`：**原曲自身就是现场版时原样返回**（否则等于自我否决）；
  否则剔除带标记的候选。全被筛掉是**合法结果**，按 `no_candidates` 交回上层 → 客户端弹锚定弹窗。
- `stream.ts` 的 `resolveTrackSource` 在**打分之前**过滤，并记一条 info 日志（滤掉几首）。
- **锚定弹窗的 `/api/tracks/:id/bili-candidates` 刻意不过滤**（代码里写了原因）：
  自动解析筛掉之后，用户恰恰需要在这里看到完整候选池、自己拍板选一条 live —— 在此过滤等于把最后的兜底也堵死。

⚠️ `matcher.ts` 的 `scoreCandidate` **一个字节没动**（文件头写明的纪律：那是唯一被真实数据验证过的算法）。

## 六、教训

1. **同一个坑修了三端，漏掉的那一端就是下一次报障**。web 与鸿蒙的注释里都写着"旧音源字节以曲目 id 缓存，不清会盖住新源"，
   iOS 这端却没有对应实现 —— 跨端对齐时要点名核对**每个端**，别只看"服务端对了"。
2. **定义了但没人调用的方法 = 死代码 = 隐患**。`AudioCacheStore.evict()` 从定义那天起零调用点，
   正因为"看着像已经有了"，才没人发现失效链路是断的。查这类 bug 先 `grep` 调用点，而不是看定义。
3. **扣分不能否决**。凡"绝对不能要"的一类东西（非录音室版本、纯音乐、鬼畜），要过滤而不是减分；
   软惩罚在对齐其他维度足够强时会被抵消，这是打分模型的固有性质。
