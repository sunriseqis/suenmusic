## 一、逐条改动

### C-1　收藏恢复静默变 0 首

**链路**：`Settings.vue` → `applyBackup()` → `batchAddFavorites()` 一次全发 → 服务端
`bodyLimit 256KB` + `tracks 最多 500 首` → 400/413 → 客户端 `catch {}` 吞掉 →
`added = 0` → 界面显示「新增 0 首 · 跳过 N」，用户以为「库里本来就有」。

**改法**：
- `api/library.ts`：`batchAddFavorites` 内部分片（400 首 / 180KB 双约束），任一批失败
  即抛错并带上「已成功写入 N 首」，返回值加 `batches`。
- `offline/backup.ts`：删掉 `catch {}`，让异常上抛（恢复是数据兜底路径，
  静默成功比报错危险得多）。

**实测**（起真服务端打真接口）：900 首一次提交 → HTTP 400（旧行为必然失败）；
按 400+400+100 分片 → 三次 200，`added` 合计 900；501 首仍被 `too_many_tracks` 拒绝。

### C-2　快速切歌把新曲音频摘掉

`load()` 用 `loadSequence` 判断「被顶掉」，被顶掉时同样 `return false` —— 与真失败共用返回值。
于是连点下一首时，第 1 次 `startCurrent` 走进失败分支，对**共享的** `<audio>` 执行
`pause + removeAttribute('src') + load()`，把第 2 次已装好的音频摘掉：界面显示第二首、实际无声。

**改法**：`startCurrent` 自己加 `startSequence`；失败收尾前与成功后的状态写入前都校验
`startSeq === startSequence`，只有「最新那次」才允许动发声体与写状态。

### C-3　DB 恢复的并发竞态（静默丢数据）

恢复流程是「关连接 → rename → 重开」。中间 `instance === null` 的窗口里，任何在飞的 handler
调 `getDatabase()` 都会**重开旧文件**并把 instance 填回去；随后 rename 覆盖路径、
`openDatabase()` 命中短路返回那个旧 inode —— 恢复"成功"了，但后续写入落进一个已被替换的
数据库文件，重启即消失。

**改法**（`server/src/db/index.ts`）：
- `DatabaseRestoringError` + `beginRestore()/endRestore()` 临界区；
- `getDatabase()` 在临界区内直接抛错（**不让请求路径自己建连接**）；
- `openDatabase()` 不检查标志 —— 恢复流程自己要靠它重开，否则死锁；
- `routes/admin.ts` 包住热替换段，并在 `migrate` 之后加 `PRAGMA quick_check` 自检（不 ok 就走回滚）；
- `app.ts` 把该错误映射成 **503 `db_restoring`**（可重试），不落到 500「未处理异常」刷日志。

**实测**：`beginRestore()` 后 `getDatabase()` 抛 `DatabaseRestoringError / db_restoring`；
`endRestore()` 后恢复可用。api-test 的「数据库恢复（覆盖式）」全链路仍 225 项全通过。

### C-4　Android `tailOnly` 索引钳制

`items` 只含 `[startIndex, 队尾)`，所以 `mediaItems.size() = 总长 - startIndex`，而
`safeStartIndex = min(startIndex, size-1)` 在 startIndex 过半后会把替换起点压到队尾附近 ——
`replaceMediaItems(from, count, items)` 覆盖到**正在播的那首**：切随机/切列表时突然跳歌。
`sameFirstId()` 读的是替换后的值，必然通过，所以静默生效、无日志。

**改法**：tailOnly 分支用绝对 `startIndex`，钳制只留给 `setMediaItems`。

### C-5　iOS `tailOnly` 不同步逻辑队列

同一路径的另一半：Swift 侧注释写「此路径下 tracks 参数只含尾段，全量逻辑队列保持不变」，
但 Web 的「切随机/切回列表」正是这条路径，传进来的已是新顺序。`self.tracks` 保持旧顺序 →
`itemIndex` 记的 `startIndex + offset` 映射到旧顺序的曲目：`tracks[currentIndex]` 取错，
表现为 trackChange 带错 id、锁屏「下一首」播错歌、封面标题错位。

**改法**：`self.tracks = Array(self.tracks[0..<startIndex]) + tracks`（越界时以传入为准），
`itemIndex` 映射随之对齐。

### C-6　iOS `reloadCurrent` 定位错位

旧实现 `remove(current)` 之后 currentItem 已变成**下一首**，再把 fresh 插到
`queue[pos-1]`（已播过的上一首）之后 —— fresh 落在播放位置之前，永远成不了 currentItem，
随后的 seek / startPlayback 全打在下一首上（用户看到「换了音源，结果开始播下一首」）。

**改法**：AVQueuePlayer 只有 `insert(_:after:)`，没有 `insert(at:)`，想让 fresh 成为
currentItem 只有整队重建一条可靠路径 —— 直接委托 `rebuildQueue(from: index, …, reason: 2)`。
代价是尾段条目重建（丢掉 next 的预缓冲），而换音源本来就是「丢缓冲重来」的语义。

### C-7　iOS 打断结束后永远没声音

`.ended` 分支是空的（保守策略：不自动恢复播放）。但系统在打断期间把 AVAudioSession 置为
非激活，`isActivated` 仍停在 true → `activateIfNeeded()` 永远短路 → 挂断电话再按播放
完全无声，必须杀 App 重开。

**改法**：`.ended` 时 `isActivated = false` + `activateIfNeeded()` + `reportPlaying(false)`，
仍然**不自动起播**（是否继续由用户按播放决定，保持原产品口径）。

### C-8　iOS 4GB LRU 对冷启动遗留文件无效

`enforceLimit` 的候选只来自 `entries`（本进程碰过的条目），而 `usedBytes()` 数的是**目录**
总大小。冷启动后旧文件占着空间却永远进不了候选集 → 缓存目录无上限增长，4GB 上限形同虚设。

**改法**：新增 `enforceLimitFromDisk()`。内存候选淘汰完还超限时扫 `*.json` sidecar，
按 sidecar 的 `lastAccess`（缺失则用文件 mtime）从旧到新删 `.bin` + sidecar。
这些文件不可能有活跃读者或进行中的下载（下载器只对内存条目存在），删除安全。
文件名是「净化前缀 + id 哈希」无法反解，所以保护对象按**文件名**比对。

### C-9　`removeAt` 不同步原生队列

同文件自己写着契约：「所有会改动队列的入口都必须调 `syncNativeQueue`」。`removeAt` 漏了 →
原生队列仍留着被删的曲目，锁屏/熄屏接续会播「已经不在队列里的歌」，`seekToIndex` 索引错位。

**改法**：删除后 `syncNativeQueue({ autoplay: wasPlaying, startPositionMs })`（整队重发，
不用 tailOnly —— 被删项可能在当前曲**之前**，尾段替换删不掉它）；队列清空时
`SuenAudio.stop()`，避免通知栏挂着空队列继续接续。

### C-10　壳内「导出备份」不落盘

`downloadBackup` 自己拼 `blob:` + `<a download>`，而安卓 WebView 对 blob 下载不触发系统下载 ——
同仓为此专门写过 `SuenNativeBackup` 桥（MediaStore 落 Downloads/SuenMusic），却零调用点。
结果：壳里点「导出」什么文件都没有，界面还报「已导出」。

**改法**：`downloadBackup` 改走 `downloadBlob`；`downloadBlob` 返回值从 `boolean` 改为
三态 `'native' | 'browser' | 'failed'`；失败抛错，成功按路径给出不同文案
（「已导出到系统下载目录」/「已交给浏览器下载」）。

### C-11　鸿蒙 `/api/**` 被 SPA 回退成 HTML

拦截器把所有指向 `http://localhost/**` 的无扩展名请求当 SPA 路由回退成 `index.html`。
未配置服务端地址时 `/api/auth/me` 会命中这条路 → 拿到 HTML → `JSON.parse` 抛
`Unexpected token '<'`，看不出真因是「没配地址」。

**改法**：拦截器对 `api/` 前缀直接 `return null` 放行给网络栈。

### C-12　鸿蒙返回键不接 `__suenBack`

**两处都是坑，只修一处没用**：
1. `web/src/native/back.ts` 的 `installBackBridge()` 用 `Capacitor.isNativePlatform()` 判定，
   鸿蒙没有 Capacitor → `window.__suenBack` **根本不存在**，ArkTS 侧怎么接都只能拿到 undefined；
2. `Index.ets` 的 `onBackPress` 只看 `accessBackward()`，浮层/搜索态下通常是 false →
   `return false` → 系统立刻退出应用（真机现象：「搜索框里按返回，App 直接没了」）。

**改法**：
- `back.ts` 改用 `isNativeShell`（Capacitor ∪ 鸿蒙）；
- `Index.ets` 的 `onBackPress` 改为「同步先吃掉 + 异步问网页」：`runJavaScript` 求值
  `__suenBack() === true` → 已消费则什么都不做；否则 `accessBackward()` 后退；历史到底
  才 `terminateSelf()`。顺序与安卓 `MainActivity` 完全一致（同一份 back.ts 契约）。

5. **C-8**：清空后重新缓存到 >4GB，冷启动一次再继续下载，检查目录体积不再无上限增长。

7. **C-10**：安卓壳内导出备份，检查 `Downloads/SuenMusic/` 真的出现文件。
8. **C-11/C-12**：鸿蒙未配地址时错误是网络错误（不是 JSON 解析错误）；浮层/搜索态按返回不退应用。

## 四、方法论记录

- **同一个 bug 常常横跨两端**：C-12 的根因在 web（`__suenBack` 不存在），症状在 ArkTS。
  只改 ArkTS 的返回值逻辑，问题依旧 —— 修「跨端契约」必须两头一起看。
- **能实测的一定要实测**：C-1 与 C-3 都起真服务端验过（400 vs 分片 200、临界区拦截），
  证据比"代码看起来对"可靠得多。
- **注释里写"保持不变"的地方最危险**：C-5 的 Swift 注释明确写「此路径下全量队列保持不变」，
  听起来自洽，但没核对消费方（`tracks[currentIndex]`）—— 设计意图与调用方假设不一致时，
  注释会变成"合理化 bug"的工具。
