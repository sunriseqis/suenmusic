## 一、逐条改动

### B-1　`.sm` 解压防护（四道闸 + 兜底）

问题：`zlib.inflateRawSync` 没有任何输出上限，而两个导入端点的 bodyLimit 放到了 20MB。
deflate 压缩比可达 1000:1 —— 20MB 全零数据压成几十 KB，解压却要真分配几十 GB。
服务端单进程跑着每日推荐与打标任务，一次 OOM 就是全部用户掉线，且**任意注册成员**都能触发。

改法（`server/src/utils/zip.ts`）：
1. 条目数闸（默认 ≤8，本格式只有 `favorites.json` + `persona.md`）；
2. 单条目解压体积闸（默认 ≤8MB，先按 central directory 声明值拦，不进 zlib）；
3. 累计体积闸（≤16MB）；
4. 压缩比闸（>100:1 拒绝）——**只对 >1MB 的条目生效**；
5. `inflateRawSync(raw, { maxOutputLength })` 作为最后一道保险：
   即使头部声明的解压后大小是伪造的，zlib 自己也会抛错。

两个端点 bodyLimit 20MB → 4MB。新增 `server/src/scripts/zip-test.ts`（14 项）并挂进 `npm test`
为 `test:zip`。

**踩坑（重要）**：压缩比闸最初写成对所有条目生效，结果一个 4KB 的重复字符文本（200:1）
被误杀 —— 而这种文件根本撑不爆内存。**闸门必须和「风险规模」绑定**：小条目由体积闸管，
压缩比闸只对大条目（>1MB）生效。测试里专门留了一项钉这个行为。

### B-2　`trustProxy` 不再无条件为真 + 节流双桶

问题：`trustProxy: true` 直接采信 `X-Forwarded-For` 最左项，而登录节流按 IP 分桶 ——
攻击者每个请求换一个伪造 IP，就永远撞不到 10 次上限，字典攻击变成无限次。

改法：
- `Config.trustProxy: boolean | string[]`，来自 `SUENMUSIC_TRUST_PROXY`：
  留空 → `false`（只信 TCP 对端）；`127.0.0.1,10.0.0.0/8` → 只信这些代理；`true` → 全信（需显式承担）。
- `app.ts` 改为 `trustProxy: config.trustProxy`。
- 节流增加**第二个不看 IP 的桶**（`account|<username>`，上限 `3 × loginMaxAttempts`）。
  实测：50 个伪造 IP 打同一账号，第 30 次被账号桶拦下（改之前是无限次）。
- `pruneLoginThrottle()` 挂进 `index.ts` 的 10 分钟清理周期，顺手根治「失败计数 Map 永不回收」
  （它本来只是 P2 的独立条目，但伪造 IP 正是把它放大成内存问题的原因，属同一威胁模型）。

代价记录：账号桶天生能被人用来「锁死某个账号一阵」，所以门槛给到 3 倍 ——
把无限次猜测压成「每窗口最多 3N 次」，同时让正常用户输错几次不至于被卡住。

### B-3　占位 JWT 密钥 fail-fast

问题：`.env.example` 里 `SUENMUSIC_JWT_SECRET=your_production_jwt_secret_change_me`，
而 `config.ts` 只判「空 vs 非空」。照抄模板部署的人会拿到一个**公开在仓库里的签名密钥**：
HS256 可离线签名，任何人可伪造 `{sub:1, typ:'access', epo:1}`（新库 token_epoch 恒为 1）
直接以管理员身份调 `/api/admin/*`。全程无运行期症状。

改法：`assertJwtSecretUsable()` 在 config 求值时执行 —— 命中占位正则黑名单或长度 <32
直接抛错并打印生成命令；`SUENMUSIC_JWT_SECRET=` 留空仍是合法状态（走临时密钥兜底 + WARN）。

⚠️ **这是破坏性变更**：如果某个部署真的照抄了模板，升级后服务端会拒绝启动。
这是刻意的（带病运行比启动失败危险得多），但发布说明必须写清。

### B-4　签名私钥移出版本库

改法：
- `git rm --cached android/app/suenmusic.keystore`（**文件保留在工作区**，不影响既有构建）；
- `android/.gitignore` 恢复 `*.jks` / `*.keystore`，并新增 `keystore.properties`；
- `app/build.gradle` 的签名口令从「硬编码 3 个 `'suenmusic'`」改为三级来源：
  `-Pandroid.injected.signing.*` → 环境变量 `SUENMUSIC_KEYSTORE_*` → `android/keystore.properties`；
  代码里**零硬编码**，缺凭据时给明确的多行警告（产物未签名，装不上也走不了自更新）；
- 新增 `android/keystore.properties.example`；本地生成了一份**未入库**的
  `android/keystore.properties` 指回既有 keystore，保证本机构建不断。

🟡 **仍需人工执行**：这把钥匙的旧口令曾随仓库公开，安全性已经不成立。
轮换步骤建议（写进发布说明）：`keytool -genkeypair` 生成新密钥 → 更新 `keystore.properties`
→ `assembleRelease` → 发版说明要求用户**卸载重装**（签名变更不能覆盖安装）。

### B-5　RemoteViews 里的裸 `<View>`

RemoteViews 的 LayoutInflater 带过滤器，只放行 `@RemoteView` 标注的类；`android.view.View`
不在其中，真机会抛 `Class not allowed to be inflated android.view.View` ——
2×2 与 2×4 两张卡片会**整体 inflate 失败**。

改法：三处发丝线（2x2 一处横向、2x4 两处竖向）改为等尺寸 `ImageView` + `importantForAccessibility="no"`，
背景仍走原来的 `@drawable/widget_divider*`。两个布局 XML 结构校验通过（真机待验）。

### B-6　补 `colors.xml`

`styles.xml` 的 `AppTheme` 引用 `@color/colorPrimary` / `colorPrimaryDark` / `colorAccent`，
而 `res/values/` 下没有任何 `colors.xml`（git 历史里也从未有过）。aapt2 link 阶段会报
`resource color/colorPrimary not found`，能否出包取决于依赖 AAR 是否碰巧定义了同名颜色。

改法：新增 `res/values/colors.xml`，取哑光调色板（#E8A33D 琥珀 / #17181B 墨黑）。

### B-7　明文 HTTP：计划口径不可行，改为三条收口

计划原写「`base-config` 关明文，改 `domain-config` 只对私有网段开」。**实测这条路走不通**：

> Network Security Config **不支持 CIDR 网段**，`<domain>` 只能写主机名或 IP 字面量。
> 而用户填的服务端地址是任意的（192.168.x.x / 10.x.x.x / 100.64.x.x + 自定义端口），
> 一旦把 base 关成 false，绝大多数自托管部署会**直接连不上** —— 这比明文的风险更大。

所以改为三条可验证的收口：
1. `SuenUpdatePlugin.download()`：新增 `isPrivateHost()`，**公网地址强制 https**，
   私网/loopback/Tailscale（100.64/10）才允许 http —— 更新包是「能被替换成任意 APK」的
   高价值目标，这条必须硬拦；
2. `Login.vue`：对「公网 + http」的服务端地址给出明文风险告警（不拦，只提示）——
   口令、访问令牌、`/api/stream/:id?t=` 的流令牌都会明文过网；
3. `network_security_config.xml` 保持放行，但把上述取舍与三条收口写进文件注释，
   避免下一个人再来「顺手收紧」一下把全端搞挂。

### B-8　nginx 上传体积

`web/nginx.conf.template` 的 `location /api/` 没有任何 `client_max_body_size`（默认 1m），
而服务端数据库恢复已放宽到 200MB、`.sm` 导入 4MB —— 反代后这些请求**一律 413**，
前端只显示「失败」。改法：加 `client_max_body_size 200m;`，并注明必须配套
`SUENMUSIC_TRUST_PROXY`，否则服务端看到的全是 nginx 的 IP（且节流会按 nginx 分桶）。

## 三、发布/升级注意事项（写进 release notes）

1. **B-3 是破坏性变更**：`SUENMUSIC_JWT_SECRET` 用了占位串或短于 32 字符的部署，升级后会
   **拒绝启动**（这是刻意的）。升级前先 `openssl rand -hex 32` 写入 `.env`。
2. **B-4 需要重新出包**：仓库里不再有私钥，构建机/CI 必须先配
   `keystore.properties` 或 `SUENMUSIC_KEYSTORE_*` 环境变量，否则产物未签名。
3. **B-8 反代部署**：`SUENMUSIC_TRUST_PROXY` 不配，服务端日志与登录节流看到的都是 nginx 的 IP。
