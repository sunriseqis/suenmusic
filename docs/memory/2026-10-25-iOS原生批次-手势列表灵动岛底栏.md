# 2026-10-25 iOS 原生批次：手势/列表/灵动岛/底栏 与 验证方法论

本文件归档 2026-10-25 夜间这一长轮的改动与踩坑（承接 `2026-10-25-iOS首次真机编译与OCR验证链路.md`）。

## 一、右滑收藏：连试四条路，最终用系统 swipe

用户报障：「手指落在歌单行上，列表完全滑不动；空白处能滑」。

| # | 方案 | 结果 |
|---|---|---|
| 1 | SwiftUI `DragGesture` + `.simultaneousGesture` | ❌ 与 `UIScrollView` 抢手势，行上滚不动 |
| 2 | UIKit `UIPanGestureRecognizer` 挂在行 `.background()` 的 representable 上 | ❌ 只挂到 `UIKitPlatformViewHost<…>`（在内容**之下**），收不到触摸 |
| 3 | 同 2，但顺祖先链找"行宿主" | ❌ SwiftUI 把 `ScrollView+LazyVStack` 的行**扁平化**了，没有独立行视图 |
| 4 | 同 2，但先转 `List`（行是真实 cell） | ⚠️ 仍只挂到 representable host，cell 祖先未命中 |
| ✅ | `List` + `.swipeActions(edge: .leading)` | 方向仲裁交给系统，滚动/滑动/下拉三者共存 |

关键认知：**hw 的 `PanGesture({ direction: PanDirection.Horizontal })` 是"方向受限手势"，iOS 的 SwiftUI `DragGesture` 没有方向约束**，
所以 hw 能同时滑行与滚列表；iOS 上等价物只能是系统 `.swipeActions`（或自绘手势栈，已证明性价比太低）。

代价：系统 swipe 露出的是 **iOS 胶囊键**，不是 hw 的"整行彩底动作区"。用户裁决：先接受系统形态。

## 二、列表全部 List 化 + 行修饰符

- 五处列表（首页新歌 / 专属 / 收藏 / 集合 / 搜索单曲）统一改 `List` + `.swipeActions`；
- 新增共享 `UI/ListRowChrome.swift` 的 `listRowChrome()`：`listRowInsets(EdgeInsets())` + `listRowSeparator(.hidden)` + `listRowBackground(.clear)`；
- 非单曲区块（海报区、榜单、AI 摘要）各作为一行，同样套 `listRowChrome()`。

## 三、曲目行不能有圆角

用户：「所有列表有一个圆角边框，web 端没有」。查 hw `pages/TrackItem.ets:260-271`：
行是**直角**，只有 `border: { left: 在播?2:0, bottom: 1 }`；`borderRadius(radiusMd)` **只属于右滑动作区**那层。
→ `TrackRow` 根节点的 `.clipShape(RoundedRectangle(radiusMd))` 改成 `.clipped()`。

## 四、灵动岛必须恒用深色配色

用户：「灵动岛不会变深浅，而且字体可读性变差」。根因两层：
1. `Palette` 取的是 `DesignTokens` 的**动态色**，widget 进程按**系统 trait** 解析 → 传对 `dark` 也没用；
   → 给 `Palette` 加 `init(dark: Bool)`（十六进制字面量，不走动态解析），widget 全部改用它；
2. **灵动岛背景由系统绘制、恒为黑**（浅色模式也一样）；浅色主题的深墨字画上去必然不可读；
   → 岛内（expanded/compact/minimal）**恒用 `dark: true`**；锁屏卡继续跟随 App 主题。
另：`.system` 模式下读 `UITraitCollection.current` 不可靠，改读前台窗口场景的 trait，并在 `colorScheme` 变化时重推 activity。

## 五、灵动岛布局：只能用单个区域自排

用户：「左封面 + 右侧四行（歌名/歌手·专辑/进度/歌词）」。第一版拆到 `.leading`/`.trailing`：
- `.leading` 太窄 → 44pt 封面被压成空白；
- `.trailing` 太高 → 四行被拉成大间距。
→ 整块放进 `.bottom` 自己 `HStack`（封面 36 + 四行 + 运输列），行距 1。

## 六、底栏：贴边与安全区

- 底栏在 `VStack` 里会停在**安全区上沿**，下方 34pt 空白 → 观感"和页面割裂、离底部太远"；
  → 背景 `.ignoresSafeArea(edges: .bottom)` 铺到底；
- 去掉 hw 的 `s3` 左右边距与 `s2` 底部边距（用户要求贴边）：标签 x 由 129…839 变为 73…861；
- **home indicator 的 34pt 不能压**（会被横条盖住），这是 iOS 与 web/hw 的结构性差异。

## 七、输入框一键清空（两端）

- iOS：`NeuInput` 加 `clearable`（有内容才显示 ×，44pt 热区），搜索页与收藏页启用；
- hw：`pages/NeuInput.ets` 加 `clearable`，同样两处启用 —— **此交互两端原本都缺**，属新增而非对齐。

## 八、本轮验证方法论（血泪）

1. **装错 App**：`DerivedData/.../App.app` 里躺着一个 **10-19 的旧 Capacitor 版**（bundle id 相同），装它会把新构建静默替换成旧 Vue 应用。
   判据：`strings -a <装好的 App>/App | grep SearchWireReply` 命中 1 才是新构建；或比对 build/installed 的 mtime+size。
2. **调试开关注入**：
   - `simctl spawn defaults write com.suenmusic.app K V` → 写的是**设备级 global domain，App 读不到**；
   - 改容器 plist 可行但 cfprefsd 会缓存，不稳定；
   - `xcrun simctl launch <bundle> -K V`（argv）时好时坏；
   - **稳定做法**：`SIMCTL_CHILD_K=V xcrun simctl launch …`；
   - 前提是 App 域里没有同名残留键（`DebugHooks` 先读 UserDefaults 再读 env）。
3. **deep link 不可用**：iOS 26 上 `simctl openurl` 会弹「在 X 中打开？」系统框，无触摸环境点不掉 → 用 `SUEN_PLAYER` 钩子。
4. **hw 构建**：`./hvigorw` 在这台机器上缺 `@ohos/hvigor-cli`（npm 源无此包）。
   可用：`DEVECO_CLI_CLT_PATH=/opt/clt/command-line-tools devecocli build`（实测 BUILD SUCCESSFUL，产出 unsigned hap）。
