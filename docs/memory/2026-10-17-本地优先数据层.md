# 本地优先数据层与直连主流程（2026-10-17）

## 数据归属变了

```
旧：服务端是唯一真相源       本地只有"快照"（offline/snapshot.ts，覆盖写、失败静默）
新：本机是真相源             服务端是可选备份（配了服务器且已登录才同步）
```

这条决定了三处实现必须跟着改，否则会互相矛盾：

| 旧实现 | 为什么现在错 |
|---|---|
| 写失败**回滚**（乐观更新） | 回滚的依据是"服务端没接受"，现在服务端只是备份，网不好不该撤销用户刚点的红心 |
| `reset()` 清空收藏 | 退出登录只是断开同步，不该删掉设备上的数据 |
| 续播只问服务端 | 断网时续播位置就读不到了，它本来就在本机 |

存储：IndexedDB `suenmusic-local`，四个仓 `favorites` / `dislikes` / `history` / `progress`。
历史 3000 条上限。`offline/localdb.ts` 是主存储，`offline/snapshot.ts` 仍是快照，两者别混。

## `serverReady()` 是必需的，不是优化

基地址为空时 `/api/xxx` 会变成**相对路径**，打到同一域名下的静态服务器，
SPA 回退返回 `index.html`（HTTP 200）→ `JSON.parse` 抛 SyntaxError。
**它既不是 ApiError，也没有 401 分支能兜住**，表现为一个莫名其妙的解析错误。
所以所有数据层入口都是「没配就别发」，不是「发了再容错」。

判据：`getBaseUrl() !== '' && getAccessToken() !== null`。

## 解析：服务端优先，直连兜底

```
有服务端且可达   → /api/resolve/:id（全局缓存，命中率高、打上游少）
服务端不可达     → 客户端自己解析（QQ 元数据 → B站搜索 → playurl）
rateLimited      → 不兜底，直接按失败返回
```

最后一条容易写错：服务端说上游正在限流时，客户端绕过去自己打上游
只会把限流拖得更久。

## 原生直连必须"登记地址"

原生播放器按 **trackId** 取地址（`SuenAudio.streamUrlFor`），`<audio>.src`
只是用来识别曲目、URL 不进播放器。所以：

```
解析出直链 → SuenAudio.setDirectUrl({id,url}) → 原生才用得上
不登记      → 原生仍拼 <baseUrl>/api/stream/<id> → 没配服务器时是空串
```

同理 `setQueue` 需要 `direct: true` 才允许空 baseUrl/token —— 旧实现没有令牌
直接 throw，于是「没配服务器 → 队列发不出去 → 点播放没反应」。

## 已知缺口（下一轮）

- 首页推荐、每日推荐、音乐画像仍然只有服务端能产出；无服务端时首页是空状态
- 锚定/换源的多候选打分还在服务端（客户端只有简化打分）
- 收藏/不喜欢的**日常增量同步**还没做（目前只在收藏页对一次账）
- 服务端的「解析缓存直链、多端共享」接口（`resolve/query`、`resolve/report`）尚未新增
