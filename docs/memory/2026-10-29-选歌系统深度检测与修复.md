## 二、三个「以为是小问题、其实很严重」的发现

### 1. seedNew 被整段挡在模型池外（不是提示词问题）

```js
ai-decide.ts:495  !usedIds.has(id) && source !== 'seedNew'
```

8 首本尊新歌**根本没进模型视野**，模型没机会写理由，`ai-flow` 只能塞占位语
「本尊新歌（必进项）」，导致 8 首无推荐语。

**教训**：这是「以为提示词能解决、其实是代码把路堵死」的典型案例，
跟用户说的「规则要写代码层不是提示词」是同一道理的反面 —— 提示词承诺了代码做不到的事。

### 2. 网友歌单池全被「消耗」，补位全落榜单

```
playlist_pool 40 份，consumed_at 全非 NULL
→ 补位只查 consumed_at IS NULL → 拿 0 行 → 全落榜单（chart 30→36）
```

`consumed_at` 的语义只是「这份歌单不再当新鲜歌单用」，**里面的歌仍是有效曲目**。
修完 playlist 从 0 → 24 首。

### 3. isJunk 的时长过滤有缝

```js
if (sec > 0 && sec < MIN_SONG_DURATION_SEC) return true;   // sec=0 时漏过
```

拿不到时长的片段正好从这个缝钻进来。改为 `sec <= 0 || sec < 90`。

第 4 条是本次最重要的语义修正：批 1 的「长理由兜底」会把审核明确 rejected 的翻回 approved，
**违反「审核觉得完全在水就丢掉、不给前端看」的规则**。改为只救「审核没工作」
（整体失败 / 模型漏回 / verdict 未识别），不覆盖「审核做了判断」。

## 四、器乐/翻唱判定改为 AI 打标（用户裁定方案 B）

**起因**：用户反馈「经常推翻唱纯音乐片段」。实测证据：
`北国之春 | 刘慧敏 | 专辑《琴意绵绵Ⅱ》| 205s` 被推了 ——
曲名干净、歌手不在名单、专辑名不含「钢琴/纯音乐」关键词，**关键词方案永远追不上器乐专辑命名**。

**方案**：迁移 026 给 `track_tags` 加 `is_instrumental`（NULL=未判定 / 0=正常 / 1=器乐翻奏片段），
`ai-tags` 打标时多问一个布尔维度，召回按字段过滤；关键词保留为第一道防线。

**注意**：这不是把「器乐」塞进风格词表（那是 2026-09-15 用户砍掉的「气质/手法」类），
而是**独立的判定维度**。

**实测**：北国之春 → `is_instrumental=1` ✅；晴天 → `0` ✅。

## 六、教训

1. **「以为是提示词问题、其实是代码把路堵死」**：seedNew 案例。改 prompt 前先确认代码路径通不通。
2. **关键词过滤永远追不上命名变化**：器乐专辑名千变万化（琴意绵绵、琴韵、指间…），
   该用 AI 语义判定就用，别硬堆关键词。
3. **语义标记要区分「未判定」和「判定为否」**：`is_instrumental` 用 NULL 表示未判定，
   不能用 0 兜底 —— 否则把「未判定」谎报成「正常歌曲」，第二道防线对新增曲目永远失效。
4. **测试数据集别按生产规模算成本**：8308 首 AI 回填我按生产算了「几块钱、1-2 小时」，
   但这是测试库，纯烧 token 没意义。涉及批量 AI 调用先问「这库是测试还是生产」。
