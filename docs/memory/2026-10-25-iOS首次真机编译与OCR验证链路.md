## 八、起播慢（像等缓存）——根因与修法

链路：`AudioEngine.streamUrl()` 原来**无条件优先** `LocalStreamProxy`（127.0.0.1）→ 代理另开 URLSession 下载 → 按 256KB 泵给 AVPlayer，
而代理首包要`等上游响应头（12s）`+`等首字节嗅探 Content-Type（3s）`。实测服务端本身 `ttfb=0.34s`，所以慢在代理的串行等待。

修法（2026-10-25）：
1. `streamUrl()` **只在整首已落盘（`AudioCacheStore.isComplete`）时**走代理；否则直连 `/api/stream`，并用 `LocalStreamProxy.shared.entry()` 后台预热缓存。
2. 代理 `metadataTimeout` 12s → **1.5s**，首字节嗅探 3s → **0.3s**。
3. 打点：`[Start] play() 进入 / 令牌就绪 / 首字节 / 首次 playing`，用于实测前后对比。

## 十一、真机「点了不出声」根因（2026-10-25 深夜定位）

**现象（用户真机）**：直接点歌不出声；有的歌暂停再播放能放，有的不行；有的下一首能放，有的不能。

**根因（模拟器日志实锤）**：`AudioEngine.rebuildQueue` 里
```
player.removeAllItems()
for i in index..<tracks.count { player.insert(makeItem(tracks[i])) }   // ← 一次插 40 首
player.seek(...)
if autoplay { startPlayback() }                                        // ← 要等 40 个插完才起播
```
每 `insert` 一次 AVPlayerItem 都要 AVFoundation 准备；实测 `[Start] setQueue 进入`（12:36:48.692）之后
**14 秒内都没打出 `rebuildQueue 结束`** —— 起播被这 40 次插入阻塞。跳到下一首时是从新下标重建（item 更少）所以快，
于是出现「点的那首不出声、下一首反而能响」的错觉。

**修法**：惰性装载 —— 只插当前 + 前瞻 2 首，剩余在进度 tick 里按需补（`ensureLookahead()`）。

## 十二、「有的歌永远不能放」不是 App 的 bug

服务端 `/api/resolve` 实测：
```
qq_003v9kAB36VVtD  ok=true  score=90  bvid=BV1gF4m1j7sB   → 可播
qq_001L6QVq4XYDwV  ok=false reason=below_threshold score=45 < 60 → /api/stream 恒 503
```
服务端日志里那串 503 就是这类曲目（AVPlayer 自己还在重试）。按既定规格：手动点播这类曲目应停在当前曲、
eyebrow 显示「无音源」，不该静默卡住 —— 惰性装载修好后会走这条路径。

## 十三、iOS「点了不出声」三个真根因（2026-10-25 全部定位）

| # | 根因 | 证据 | 修法 |
|---|---|---|---|
| 1 | `rebuildQueue` **一次 insert 队列里全部 40 首** AVPlayerItem，`startPlayback()` 在循环之后才调用 | 日志：`setQueue 进入 tracks=40` 之后 14s 内没有 `rebuildQueue 结束` | **惰性装载**：只插当前 + 前瞻 2 首，其余在进度 tick 里 `ensureLookahead()` 补 |
| 2 | `startPlayback()` 里 `guard playingIntent` 把起播挡掉 | 日志：`rebuildQueue 结束 autoplay=true … intent=false` | 起播时把意图立起来（`playingIntent = true`） |
| 3 | **服务端 `/api/stream` 回 `application/octet-stream`**；iOS AVPlayer 认 MIME、不自己嗅探 | mac 上 `AVURLAsset` 直测该 URL → `-11828 不支持此媒体的格式`；强制 `audio/mp4` 后 `isPlayable=true / tracks=1 / 268.5s` | **服务端按首块嗅探**（`sniffAudioType`）把 content-type 改写成 `audio/mp4`，独立 1KB 探针 + 10 分钟缓存 |

第 3 条是**关键回归点**：本地代理里本来有 `playableContentType()` 会修 MIME，我为「起播快」改成直连后绕过了它 ——
而直连的 URL 上游只给 octet-stream，于是「点了就是不出声」。现在服务端把 MIME 报对，直连即可。

**已验证**：`/api/stream` 的 `Range: bytes=0-1` 探针与 `bytes=0-524287` 大区间都回 `content-type: audio/mp4`，
且 524288 字节完整（嗅探不能截断流 —— 踩过 `for await … return` 会 destroy 流、只剩 15.9KB 的坑）。

**待验证**：iOS 端在服务端修好后跑一次 autoplay，确认 `[Diag] pos` 会推进（最后一次脚本没触发到 autoplay 钩子）。

## 十四、**「点了不出声」最终根因（旧仓早就记过，我这次丢了这根线）**

旧仓 `docs/architecture/ios-plan.md` §10 与 `SuenAudioCache.swift` 里 2026-09-26 的实测记录，
一字不差地描述了我们这次的现象：

> 服务端 `streamRate()` 对**带 Range 的请求**按码率限速（`max(码率*1.3, 40_000)`，下限 40KB/s），
> 而 AVFoundation 在 40KB/s 下**打不开 B 站 fMP4** —— 一直停在
> `AVPlayerWaitingWhileEvaluatingBufferingRateReason`，20s 从未就绪，还不断从 64KB 对齐偏移重发。
> 390KB/s / 1MB/s 则立刻 readyToPlay。修法：**iOS 本地代理的首次整卡拉取不带 Range**
> （服务端 `if (!hasRange) return undefined`，明确不节流）。

**我们这次真正的断线**：`LocalStreamProxy.configure(base:token:)` 存在，但 `AudioEngine.setQueue`
**从来没调用它** → 代理 `upstreamBase` 为空 → `localURL()` 返回 nil → 播放全程**直连**
→ AVPlayer 用 Range 拉流 → 被 40KB/s 限速 → fMP4 打不开 → 卡死不出声。

修复（`71909ea` 之后）：`setQueue` 里 `LocalStreamProxy.shared.configure(base:token:)`，
播放回到代理路径（代理首次整卡拉不带 Range → 不节流 → 快速喂给 AVPlayer）。

实测通过：
```
[Diag] tcs=2 item=1(readyToPlay) pos=0 → 2000 → 4500 → 6500 → 9000ms rate=1.0 err=-
```

### 同批修掉的另外三条（都有独立证据）
1. **队列一次性 insert 40 首** → 起播被阻塞 10s+：改惰性装载（当前 + 前瞻 2）。
2. **`startPlayback` 的 `guard playingIntent`** 把起播挡掉（日志 `intent=false`）：起播时立意图。
3. **服务端 MIME `application/octet-stream`** → AVFoundation 直接 -11828（旧仓也记过这条：
   `audio/mp4`/`video/mp4` 都行、octet-stream 拒播）：改为按首块嗅探，且**必须在 `reply.send()` 之前**覆盖
   （HEAD 探针也要对，否则 AVFoundation 预探看到 octet-stream 就放弃）。

另外给节流加了**起始 2MB 字节级突发**（`createThrottle(..., burstBytes)`）：即使走直连，
AVPlayer 也能先拿到足够数据起播，后续再按码率节流，上行保护目标不变。

## 十七、歌曲长度不对（锚定曲目）

现象：锚定过的曲目（指到时长不同的 B 站视频）进度条总长不对。

根因：`AudioEngine.currentItemDurationMs()` 取的是 `AVPlayerItem.duration`，回退到**曲目元数据 `dt`**（QQ 的时长）。
而手动锚定允许把一首歌指到时长完全不同的视频 —— 服务端其实已经把**真实时长**放在流响应头
`X-Audio-Duration-Ms` 里（代理也解析进了 `AudioCacheEntry.declaredDurationMs`），但引擎从没读它。

修法（取值优先级）：
1. `AudioCacheStore.realDurationMs(trackId)` 读代理解析到的 `X-Audio-Duration-Ms`（**首选**）；
2. 其次 `AVPlayerItem.duration`；
3. 最后才回退元数据 `dt`。

实测（qq_003v9kAB36VVtD，锚定 BV1gF4m1j7sB）：
```
[Diag] pos=4000ms dur=269000ms  ← 服务端 X-Audio-Duration-Ms = 269000（4:29）
```
与响应头完全一致；修前这里会是 QQ 元数据的 dt。

## 二十、起播慢的**真根因**：服务端上行节流（不是解析、不是客户端）

用户的质疑是对的：「hw 端同一个服务端，起播 2 秒内」。我把变量一个个排除后，落在**节流**上。

### 判定链（都在 mac 上用裸 AVPlayer 打真实 URL，量到 `readyToPlay`）
```
服务端 /api/stream 首字节 ttfb：冷曲目解析后 0.04s、热曲目 0.09s        ← 服务端不慢
/api/resolve?force=1：0.18-0.73s                                      ← 解析不慢
play_sources=65 / tracks=3749                                        ← 98% 冷，但不是主因
裸 AVPlayer 打同一 URL：
  节流 40KB/s（原参数）     → ready 8.6-9.2s     ❌
  起始突发 2MB              → ready 8.6-9.2s     ❌
  起始突发 4MB              → ready 1.9s / 8.6s  ⚠️ 不稳
  不节流                    → ready 0.76-0.79s   ✅
  起始突发 12MB（最终）      → ready 0.49-1.60s   ✅
```

**结论**：AVFoundation 要攒**很大一段前缀**才肯 `readyToPlay`；服务端按「码率×1.3、下限 40KB/s」节流，
攒够要 9 秒。鸿蒙的播放器只需少量数据就能开播 —— 所以**同一个服务端，hw 2 秒内、iOS 9 秒**。
这解释了我们之前所有互相矛盾的观测。

### 修法
`createThrottle` 的起始突发额度 2MB → **12MB**（覆盖我们 5-7MB 的音频文件）；
节流仍对「超大文件 / 并发多流」生效，上行保护目标不变。

```
idx=15  qq_000X0ovk3knKI6  resolve ok=false score=0  → /api/stream 503（真·无音源）
```
→ **可播曲目全部 1.1-1.3s 起播**；剩下两首是服务端确实没有音源，按规格应显示「无音源」。

## 二十一、无音源语义对齐 hw（2026-10-25）

hw 规格（`MediaPlayerCore`）：`NO_SOURCE_LABEL='无音源'`；手动点播失败 → **不跳、不弹按钮**，只在
「正在播放」那行显示「无音源」；列表连播失败 → 600ms **静默跳过**；连续失败 → 通知 + 暂停。

iOS 侧 `PlaybackService.settleFailure` 的三分支本来就照这个写的，但**根本走不到**，原因有两个：

1. **失败检测挂在进度 tick 上**（`onProgressTick` → `reportCurrentItemFailureIfNeeded`）。
   服务端 503（曲目真没音源）时 item 立刻 failed，而**吃不上饭的播放器没有时间轴** → 周期观察者
   永不回调 → 失败传不出去 → 三分支全都不执行，用户看到「点了没反应也没提示」。
   **修法**：`makeItem` 里 KVO 监听 `item.status`，`.failed` 立即上报（`itemObservations` 持有）。
2. **引擎自己会跳歌**：`handlePlaybackFailure()` 失败 0.3s 后 `rebuildQueue(next, reason: 1)`，
   而 `emitTrackChange(reason: 1)` 会把 `manualLoad` 重置为 false —— 于是「手动点播就停住」永远走不到，
   用户想锚定的那首还会被自动切走（hw 代码里专门写死不许这样）。
   **修法**：引擎失败只报告（`reportPlaying(false)`），策略全部交给 `PlaybackService.settleFailure`。

实测（模拟器，服务端确实无音源的两首 qq_001nqmCk3H59NF / qq_000X0ovk3knKI6）：
```
[Start] item failed: 无可用资源
[Fail] 手动点播无音源 → 停在当前曲，eyebrow 显示「无音源」（不跳、不弹按钮）
```
屏幕 OCR 也在底部播放条读到「无音源」（`PlayerBar` 第二行改为显示该文案，danger 色）。

**仍未对齐的一处**：hw 的「更多 → 修正音源」入口（手动锚定）iOS 还没有 —— 属既有待办
「播放页歌词面板 + 更多菜单」，不在本次范围。

## 二十二、系统通知（`Notifier`）补齐前台展示（2026-10-25）

`Notifier` 早就有（对齐 hw `common/Notifier.ets`），但有两个会让通知**实际看不见**的缺口：

1. **App 在前台时 iOS 默认不弹本地通知** —— 必须实现 `UNUserNotificationCenterDelegate.willPresent`。
   而我们的通知场景（列表连播失败自动跳过、连续失败暂停）几乎都发生在用户正看着 App 的时候，
   不实现等于「通知发了但永远看不到」。
2. **授权只在第一次失败时才请求** —— 系统弹框出现在最不合适的时刻，且用户若当时忽略就一直没授权。
   改成 App 启动即 `Notifier.bootstrap()`：装 delegate + 申请授权，并打一条授权状态日志。

实测（模拟器）：
```
[Notify] 授权状态=2（已授权）
前台横幅 OCR：没有匹配音源 / 《测试曲目》没有可播放的匹配音源，已自动跳过 / 现在
```
（自检钩子 `SUEN_TEST_NOTIFY=1`，仅 DEBUG、默认关闭。）

### 通知触发点（与 hw 一致）
| 场景 | 通知 | 页面提示 |
|---|---|---|
| 手动点播失败 | **不发**（用户就在页面上）| eyebrow / 播放条显示「无音源」|
| 列表连播失败自动跳过 | 发「没有匹配音源」| 不留任何报错 |
| 连续多首失败 | 发「连续多首没有匹配音源」+ 暂停 | 不留报错 |

## 二十三、Live Activity 关掉（系统自己就渲染媒体播放）— 2026-10-25 定案

用户质疑：
> 旧仓没有这个（锁屏）面板，但是真机灵动岛是有内容的，虽然和现在不一样。查查看，
> 系统会不会自动渲染媒体播放，而必须要 live？

**查证结果：旧仓完全没有 ActivityKit**。
```
grep -rn 'ActivityKit|ActivityAttributes|ActivityConfiguration|WidgetKit' ios/  → 0 命中
grep -c 'SuenWidgets|appex' ios/App/App.xcodeproj/project.pbxproj                  → 0
```
而真机上灵动岛**照样有内容** —— 结论：**iOS 系统自己会把当前媒体播放渲染到灵动岛与锁屏**
（`MPNowPlayingInfoCenter` 就够了），不需要我们声明 Live Activity。

反过来，一旦声明 Live Activity，按 Apple 文档「must support all presentations」，
锁屏必然多出一张卡（与系统媒体卡重复），之前返回 EmptyView 还留下一个**空壳面板**。

### 决定
`LiveActivityController.enabled = false`（默认关闭）：
- 锁屏只保留系统媒体卡，不再有我们的卡 / 空壳面板；
- 灵动岛交给系统渲染；
- 代码与 `SuenWidgets` 扩展**保留**（不删），将来若要「系统卡给不了的内容」（例如歌词滚动）再打开开关 ——
  但要接受随之而来的锁屏卡片。

### 连带影响
本次实现的歌词链路（`/api/lyrics` → LRC 解析 → `ContentState.lyricLine` → 锁屏/灵动岛渲染）随之**休眠**：
系统渲染的媒体卡不带歌词，要歌词就必须开 Live Activity。
