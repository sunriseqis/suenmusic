## 二、调查结论（按重要度排序）

### 结论 1：「tab 点击失效」悬案翻案 —— 不是 tab bug，是歌词层逃生口问题 ✅ 已定案

上一轮记录在案的未解悬案「设置页上 tab 点击不导航」实为**误诊**：

- **误诊原理**：`uitest dumpLayout` 的可访问性树包含**已挂载但被盖住的隐藏层**（Settings 页节点在树里，但屏幕上可见的是播放页歌词层）。上一轮仅凭 dump 判断「已到设置页」，导致整条调查路线跑偏。
- **真相**：点击「设置」tab 后 Settings 页确实挂载了，但播放页**歌词层（`sheet='lyrics'`，整页 Column 全屏）叠在上面盖住 tab 栏**。后续所有「tab 点击」都落在歌词层上 = 无效点击。屏幕实际显示的是「歌词 · 我们俩」整页歌词。
- **与用户反馈互证**：这正是用户自己说的「找不到关闭按钮才回不到 tab 页」——歌词层唯一出口是右上角收起钮（`WebIconButton CHEVRON_DOWN`，36vp 键壳），图标太小找不到。
- **修复方向（恢复时做）**：歌词层收起钮加大/加明显（≥44vp 触控区），顶栏整条可点收起。**tab 栏本身无 bug，不要去动 NativeRoot 的 tab 逻辑。**

### 结论 2：黑名单弹窗行错乱确诊（新 bug，比「图标大」严重）🔴 根因 95% 锁定

用户截图 u01（设置页·本机 tab + 黑名单弹窗）像素实测：

- 5 个黑名单行全部渲染成**全宽大板**：歌名文字完全消失（Text 被挤成 0 宽），「恢复」按钮膨胀到 ~960px 宽（≈整行宽）× 107px 高（30vp）。
- 佐证：u04（数据备份弹窗）的按钮也异常偏大（两个并排按钮各 ~500px 宽；底部有一块 ~670×140px 的巨型亮块）。
- **根因（WebButtons.ets，高置信）**：`WebButton` 在 `blockFlag=false` 时根 Stack `.width(undefined)`（靠内容自适应），但内部**顶沿高光 Row 是 `.width('100%')`** —— 百分比宽子组件在内容自适应容器里按父级的**最大可用约束**测量 → Stack 被撑到父容器全部剩余宽度；配合 `Stack({ alignContent: Alignment.Top })`（= 顶部**水平居中**），label 渲染在巨板顶部居中。行内 `Text(row.name).layoutWeight(1)` 被先测量的巨宽按钮挤压成 0 → 歌名消失。
- **修复方向**：`WebButtons.ets` 去掉 sheen Row 的 `'100%'` 依赖（方案任选：sheen 改 Stack 顶部 border；或 sheen 不进 Stack 而用绝对定位；或非 block 时给 Stack `constraintSize` 收口）。修完后**全端 32 处 `WebButton({` 调用点**逐一复验（黑名单行、备份弹窗、锚定弹窗、ServerListPage、QueueView、LyricView、EmptyState 等）。
- **注意**：`WebIconButton`（WebIcons.ets）的 sheen 已用 `.position({x:0,y:0})` 钉住、且键壳有显式 `boxSize`，**无此问题**（u07 搜索按钮正常即为证）。

### 结论 3：toast 漂移证实（用户反馈第 3 条后半）✅ 截图证实

u08（播放页）显示「后续不再推荐歌手「郭顶」」出现在**屏幕顶部**（与 eyebrow「已停止 · 每日推荐」重叠区域），非标准底部 toast 位。修复时查 `showToast` 的定位（`getUIContext().getPromptAction().showToast` 默认应在底部，漂到顶部偏右需实测定位参数/是否被别的渲染顶上去）。

### 结论 4：播放页不喜欢按钮现状证实 ✅ 截图证实

u08 显示推荐卡上的不喜欢入口 = `WebIcon(DISLIKE_SONG 14) + Text「不喜欢」+ chevron`（带文字），与用户要求「图标不需要文字」直接对应。重造方向不变：单一 dislike 图标钮 → 点击弹窗选「这首歌/这位歌手」→ 落地后 toast（位置修复后）+ 队列摘除 + bumpDailyRefresh。

### 结论 5：设置页截图未见图标挤压 —— 反馈第 2 条范围收窄 ⚠️ 待补取证
