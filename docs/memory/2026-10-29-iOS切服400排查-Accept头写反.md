# 2026-10-29 · iOS 切服 400 排查：Accept 头参数写反

> **归档类型**：疑难 bug 定位记录（过程比结论更有价值）
> 关联：[iOS 端到端验证](2026-10-29-iOS端到端验证.md)、
> [iOS 播放内核切换 libmpv](../plan/2026-10-28-iOS播放内核切换libmpv.md)

## 一、现象（用户真机反馈）

同一账号在三个地址之间切换时失败：

```
局域网   http://192.168.89.3:8904      ← 可用，登录正常
反代     https://yy.813112.xyz:89      ← 家宽 IPv6 反代（A 记录指向一台路由器）
隧道     https://yy.suenqi.cc.cd       ← Cloudflare 隧道
```

- 切反代偶发「切换失败：连不上该服务器」，偶发「服务端返回 HTTP 400」
- **一旦失败，之后切局域网和隧道全部失败**，只能重新登录恢复
- **鸿蒙端同一账号、同一域名完全无此问题** ← 关键线索

## 二、根因：`setValue` 两个参数顺序写反

```swift
req.setValue("Accept", forHTTPHeaderField: "application/json")
//            ↑ 值                      ↑ 头名          ← 反了
```

实际发出的是一个**非法 HTTP 头** `application/json: Accept` —— 头名里带 `/`，
违反 RFC 7230 的 token 语法，服务端解析器直接判 400。

正确写法：

```swift
req.setValue("application/json", forHTTPHeaderField: "Accept")
```

### 为什么只有 iOS、只有切服有

| 维度 | 说明 |
| :-- | :-- |
| **只有切服有** | 主请求管线 `APIClient.send` **根本没设 Accept 头**，只有切服验证的两处直连 HTTP 设了（`ServerListSheet.send` 与 `APIClient.directJSON`） |
| **只有 iOS 有** | 鸿蒙端 `http.createHttp()` 的 header 用**对象字面量**设置，不存在这种位置参数错位 |

## 三、抓到的原始请求（决定性证据）

在 Mac 上起一个 dump server，把 Swift URLSession 的原始请求打出来：

```
POST /api/auth/refresh HTTP/1.1
Host: 127.0.0.1:18080
Content-Type: application/json
User-Agent: swift-frontend (unknown version) CFNetwork/3860.700.1 Darwin/25.6.0
Connection: keep-alive
Accept: */*                     ← URLSession 的默认值
application/json: Accept        ← ★ 我们写反的那个头

BODY: {"refreshToken":"probe_dummy_token_1234567890"}
```

## 四、对照实验（一锤定音）

```
【错误写法】application/json: Accept → HTTP 400 {"error":"Bad Request","message":"Client Error","statusCode":400}
【正确写法】Accept: application/json → HTTP 401 {"error":{"code":"unauthorized","message":"刷新令牌无效或已过期"}}
```

## 五、为什么这个 bug 藏了这么久

1. **错误响应格式不是我们自己的**
   我们服务的 400 是 `{"error":{"code":"bad_request","message":"..."}}`，
   而实际收到的是 `{"error":"Bad Request","message":"Client Error","statusCode":400}` ——
   这是 Node/Fastify 的**解析层**错误，说明**请求根本没进到业务代码**。
   → 一直在服务端日志里找，方向就错了。

2. **curl 通 ≠ App 通**
   `curl -X POST ... -H 'Content-Type: application/json'` 打同一地址、同一个令牌 → 200/401 正常。
   curl 不带那个非法头，所以永远复现不出来。
   → 必须用**和 App 相同的 HTTP 客户端**（Swift URLSession）验证。

3. **只在切服路径触发**
   主请求管线没设 Accept，所以首页、播放、每日推荐全都正常，
   只有「切换服务器」这一个动作会 400 —— 容易被误判成「切服逻辑有问题」。

## 六、复现方法（可复用）

模拟器 + 真实三地址，用 `pfctl` 只阻断局域网端口来模拟「断 WiFi 走蜂窝」：

```bash
# 只断局域网，反代/隧道仍通（等价于手机断 WiFi 走移动网络）
printf 'block drop quick on en0 proto tcp from any to 192.168.89.3 port 8904\npass all\n' > /tmp/pf.conf
sudo pfctl -f /tmp/pf.conf && sudo pfctl -e

# 复现路径
# 1) base 置死地址 → 2) 断局域网 → 3) 启动触发 failover → 4) base 变反代
# 5) 恢复局域网 → 6) 切回局域网
```

结果：

```
改前  [SwitchTest] → http://192.168.89.3:8904 FAIL: 服务端返回 HTTP 400
改后  [SwitchTest] → http://192.168.89.3:8904 OK
三向连续切换（局域网→反代→隧道→局域网→反代）全部 OK，令牌全程 43 字符未丢
```

## 七、连带修掉的两个真 bug

### 1. 登录会清空服务器列表

```swift
// AppState.login 原实现
ServerRouter.shared.save(candidates: [ServerCandidate(url: addr, name: "默认")])
```

**整表覆盖** —— 重新登录一次就把用户已配置的反代/隧道全删了，多服务端形同虚设。
改为：只在列表里还没有该地址时 `append` 一条。

### 2. 切服刷新成功后不落盘 → 一次失败即永久登出

`verifyAccount` 原来是「刷新 + `me` 两步都成功才 `adopt`」。但 `/api/auth/refresh` 是**轮换语义**
（旧令牌立即吊销）—— 第 ② 步失败时新令牌被丢弃，客户端只剩已吊销的旧令牌，之后切**任何**服务器都 401。

hw 端 `refresh()` 一直是在函数内立刻 `putSync` 落盘的，所以那边从没这个问题。

改法（对齐 hw）：
- 新增 `APIClient.rotateTokens(on:)`：刷新成功**立刻落盘**，单飞槽位 `rotationTask` 与常规 401 刷新共用
- 新增 `APIClient.directJSON(...)`：直连指定 base 的最小 HTTP（不走选路重放 / 不走 401 自动刷新）
- `verifyAccount` 改为：① `rotateTokens(on: base)` ② `/api/auth/me`

## 八、教训

1. **错误响应格式不是自己的 → 请求没到自己的服务**。别在业务日志里找，去看原始请求。
2. **curl 通 ≠ App 通**。默认请求头不同，必须用同一个 HTTP 客户端验证。
3. **「参数写反」这类错误读代码看不出来**，只有抓原始请求才能发现。
4. **平台间行为差异是线索不是借口**：「HW 没这个问题」直接指向 iOS 实现特有的写法。
5. **轮换式令牌，刷新成功必须立刻落盘**，不能攒到后续步骤都成功再存。
