## 四、fnOS：按官方手册修正数据目录

用户提出「默认数据目录是 `/`」—— 查证后确认是真问题（我先前只评为 P3，评低了）。

**根因**：`VAR_DIR="${TRIM_PKGVAR}"` 无空值保护，为空时 `DATA_DIR` 退化成 `/data`、日志 `/info.log`、PID `/app.pid` —— 直接写根分区。

**官方手册（developer.fnnas.com）确认的约束**：

- 安装后 `/var/apps/{appname}`，`target`→`@appcenter`、`etc`→`@appconf`、`var`→`@appdata`、`home`→`@apphome`；
  **「请使用 TRIM_APPDEST / TRIM_PKGETC / TRIM_PKGVAR 等环境变量，不要硬编码路径」**。
- **用户要在文件管理器看到/管理数据，必须在 `config/resource` 声明 `data-share`**，
  路径来自 `TRIM_DATA_SHARE_PATHS` 或 `/var/apps/{app}/share/...`。
- `/app/{appname}` 是**统一网关的 URL 前缀**（`http://NAS/app/notepad`），**不是文件系统路径** ——
  这条澄清了「数据应该在 /app/suenmusic」的记忆偏差。

**落地**：

1. 路径三道保险：反推（`cmd/` 上一级 = 安装目录；其父级 `/var` = 数据目录）+ 兜底（每个回调脚本同样处理，拿不到退 `/dev/null`）+ 硬闸（`"" | "/" | "/var" | "/usr" | "/tmp"` 一律 FATAL 拒绝启动）。
2. `config/resource` 从 `{}` 改为 `{"data-share":{"shares":[{"name":"suenmusic/backup"}]}}` ——
   **只放备份**；数据库本体仍留在 `var` 私有区（误删不可逆的东西不放可见区）。
3. 配置从 `var` 迁到 `etc`（`TRIM_PKGETC`，官方语义），兼容读旧位置。
4. `main` 导出 `SUENMUSIC_BACKUP_DIR`（取 `TRIM_DATA_SHARE_PATHS` 第一项）/`SUENMUSIC_BACKUP_KEEP`，启动日志第一行打印四个目录。

**实测**：不设 `TRIM_*` → 反推到 `<pkg>/var/data` 且根目录干净；`TRIM_PKGVAR=/` → FATAL 拒绝启动；
备份脚本产出文件落在 `share/backup/`；`env.example` 落在 `etc/`。

## 六、教训

1. **「顺手加的 API」最容易变死码**：`isRestoring()`、`loginThrottleSize()` 是我上一轮写防护时加的，零调用 —— 本轮自己删掉。
2. **删除必须先查依赖，不能只看名字**：`sources/qq/plaza.ts` 看着像 plaza 的一部分，其实被每日推荐用着；删路由保留源，才是对的。
3. **脚本化删代码块很危险**：用括号配平法一次性删了 3 个文件的函数，把 `formatCount` 这类相邻导出也切掉了；靠 `vue-tsc` 才发现。最终稳妥做法是「按行号 + 断言首尾标记」逐段删，每删一组过一遍类型检查。
4. **`noUnusedLocals` 是删除时的安全网**：Web 打开着它，删完 tsc 立刻报未用 import，比人工核对可靠。
5. **官方文档要读到「这条路径是什么」为止**：`/app/xxx` 与 `@appdata/xxx` 一字之差，一个是 URL 一个是磁盘。

### 7.2 调研纠正了我两处判断

1. **`AVPlayerItem.automaticallyWaitsToMinimizeStalling` 不存在**（该页 404），只有 `AVPlayer` 上有；`AVPlayerItem` 侧只有 `preferredForwardBufferDuration`。
2. **鸿蒙 `onInterceptRequest` 不能拿来做流式缓存**：官方明说它「不支持分片缓冲（buffer）类型数据」，也没有 Range 偏移参数。要做「按 Range 分块回字节」必须用 **`WebSchemeHandler`**（API 12+：`onRequestStart` 能拿到含 `Range` 的完整请求头，`WebResourceHandler.didReceiveResponseBody` 分块回）。

### 7.3 鸿蒙的正解（待实施）

官方有专门的 **「托管网页中的媒体播放」** 通道：
`.enableNativeMediaPlayer({ enable, shouldOverlay })` + `controller.onCreateNativeMediaPlayer(handler, mediaInfo)` 返回实现 `webview.NativeMediaPlayerBridge` 的实例（API 12+），官方示例内部播放器就是 `media.AVPlayer`，且明确「**纯音频无需设置 surfaceId**」。

一次性解决三件事：后台出声（不再依赖 WebView audio 在后台是否存活）、缓存（AVPlayer + 我们自己的缓存层）、弱网重试（原生可控）。**网页代码基本不动**，只是把声音交给原生。
配套硬约束（官方文档确认）：
- `STREAM_USAGE_MUSIC` 场景必须接 AVSession + 申请 `AUDIO_PLAYBACK` 长时任务，否则退后台被静音冻结；暂停/停止时应**主动取消**长时任务（我们现在的 30s 延迟偏保守）；长时任务有「申请了但没在播 → 挂起」的一致性校验。
- 离线缓存必须落 **`filesDir`**：官方明说 `cacheDir` 会被系统按配额自动清理。
- `http.request` 单次响应 ≤5MB（API 23 起 50MB）→ 拉整首歌要用 `requestInStream` 或 `request.agent`（其 `FileSpec.begins/ends` 就是 HTTP Range，天然断点续传）。
- 唯一**未被文档背书**的假设：WebView 里的 `<audio>` 退后台是否真出声、是否满足长时任务一致性校验 —— 全站无任何文字，必须真机验证（这本身也是做接管的理由）。

- GitHub Issues 搜 `enableNativeMediaPlayer` / `onCreateNativeMediaPlayer`：**各 0 命中**。
- 官方样例**存在**：`applications_app_samples / code/DocsSample/ArkWeb/UsingWebMultimedia`
