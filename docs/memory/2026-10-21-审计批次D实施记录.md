## 一、逐条改动

### D-1　JWT 密钥持久化（本批最重要的一条）

`fn/cmd/main` 以前只导出 HOST/PORT/DB/WEB_ROOT/TZ，**不导出 `SUENMUSIC_JWT_SECRET`**。
服务端 `config.ts` 在密钥为空时随机生成 —— 于是每次重启/升级都换密钥：

- 访问令牌全废 → 原生端被迫重新登录；
- 6 小时**流令牌全废** → 正在播放的歌直接 403 中断；
- Web cookie 会话因为走库里的刷新令牌，倒是能自愈（所以这个问题在 Web 上看起来"只是偶尔要重登"）。

**改法**：`ensure_jwt_secret()` —— 首次启动用 `openssl rand -hex 32`（没有 openssl 时退回
`node -e crypto.randomBytes`）生成，`umask 077` + `chmod 600` 落到
`${TRIM_PKGVAR}/data/jwt.secret`，之后每次 `cat` 出来 export。

**实测**：重启前后 `md5sum` 一致；服务端日志里「未配置 SUENMUSIC_JWT_SECRET，已生成临时密钥」
出现 **0 次**。

### D-2　升级前必须停旧进程

`upgrade_init` / `upgrade_callback` 都是裸 `exit 0`。后果是：文件被替换，但旧进程已经把代码
读进内存 → 用户仍在用旧版本；而 `main start` 读到存活的 PID 判为「已在运行」直接返回 0
→ **整个升级过程服务从未真正重启**，界面却显示成功。

**改法**：
- `upgrade_init`：调 `main stop`，然后轮询端口最多 20 秒等它真正释放
  （新进程起来时旧进程还占着 3210 就是 EADDRINUSE）；任何失败都不阻断升级（`exit 0`）。
- `upgrade_callback`：调 `main start`，再打 `/api/health`（最多等 30s）把返回的
  `version` 写进 `info.log` —— 事后查「到底跑的是不是新版」不用再猜。

### D-3　守护进程

以前 `nohup node &` 一次性拉起，崩溃/OOM 后不重启；而 `fn/manifest` 里 `checkport = true`
让应用中心以为服务还活着。

**改法**：同一个脚本加 `__supervise` 模式（由 `start_process` 用 `nohup` 拉起）：
`trap cleanup TERM INT` 收停止信号 → 停子进程 → 退出；子进程异常退出则 `sleep 5` 后重启。
子进程 pid 单独写 `app.child.pid`。

**实测**：`kill -9` 子进程 → 9 秒内自动拉起新进程（pid 变化）且 `/api/health` 恢复。

### D-4　stop/status 的可靠性

以前 PID 文件只有 pid，PID 被系统复用时会误杀无关进程；PID 文件丢了则彻底停不掉。

**改法**：
- PID 文件记录 `pid + starttime`（`/proc/<pid>/stat` 第 22 字段；用 `sed 's/^[^)]*) //'` 先处理
  可能含空格/括号的 comm 字段，再取第 20 列）；
- `status`：PID 双校验命中 **或** 端口有人在听，任一即视为运行中（100 号退出码 3）；
- `stop`：先置 `stop.flag`（守护循环看到就不再重启子进程）→ TERM 守护进程并等 15s
  → 仍在则 KILL → 补收可能滞留的子进程 → 清 PID 文件 → **校验端口真的释放**，
  没释放就返回非零并 WARN（很可能是旧版本遗留的进程）。

**实测**：`stop` 后 `status` 返回 3、端口释放、`ps` 无残留。

### D-5　生产依赖必须重装，不能拷

以前是「`server/node_modules` 存在就整个 `cp`」。构建机上只要装了 devDependencies
（我本地 `npm ci` 装了 typescript / @types/node），typescript、@types 就会一起进包：
白占体积，而且「这个包到底带了哪些依赖」不可复现。

**改法**：一律 `npm ci --omit=dev --no-audit --no-fund` 到 `fn/app/server/`，
装完再校验 `node_modules` 里没有 `typescript` / `@types`，**有就直接拒绝出包**。

### D-6　陈旧 `web/dist` 也照样打包

只判断 `index.html` 存在是不够的：改了 `web/src` 没重新 build，新 fpk 里前端还是旧版本，
而包体积、校验和一切正常 —— 这种问题几乎无法从产物看出来。

**改法**：`newestMtime()` 递归取 `web/src`（含 `index.html` / `vite.config.ts` / `package.json`）
的最新 mtime，与 `web/dist` 的最新 mtime 比，源码更新则强制 `npm run build`。

**实测**：`touch web/src/main.ts` 后判定从 `false` 翻转为 `true`。

### D-7　日志轮转 + 运维文档

- `rotate_log()`：`info.log` > 8MB 轮转为 `info.log.1`（以前无限增长，NAS 盘被日志吃满过）；
- 新增 `docs/dev/fnos-ops.md`：安装布局、启停、守护、密钥/数据库落点、端口与信任代理，
  以及 **命令行运维必须显式传 `SUENMUSIC_DB`** ——
  在包目录里直接跑 `user-add` / `db-backup` 会按默认相对路径在**包安装目录**里新建空库，
  命令"成功"了但数据在升级时被整体替换；
- README 挂链接并修正产物名（实际是 `suenmusic-v<version>.fpk`，原文写的是
  `suenmusic-<version>.fpk`）。

## 二、写的过程中被自己测出来的两个 bug（值得记）

第一次在假安装目录里 `start` 时，日志出现 `line 163: : command not found` + `code=127`
无限重启：

1. **`NODE_BIN` 不跨进程继承**：它在 `start_process` 里赋值但没有 `export`，而守护进程是
   **新起的 bash**（`nohup "$SELF" __supervise`）→ 拿到空值 → 那行变成空命令（bash 报
   `: command not found`）。修法：`start_process` 里 `export NODE_BIN`，并且 `supervise()`
   自己再 `find_node` 解析一次（两个入口各备一份，不依赖继承）。
2. **`TZ` 设得太晚**：`export TZ` 原本在 `start_process` 里，而脚本开头几行日志在那之前写，
   于是同一个 `info.log` 里出现 UTC 与 +08 混排（`16:29` 与 `00:29` 交错，初看像时钟错乱）。
   修法：`TZ` 提到脚本顶部，日志时间戳全脚本统一。

两个都是"只有在真环境跑一次才会暴露"的类型，纯读代码看不出来。

另外一个副作用教训：清理测试进程时用 `pkill -f "fnk"` 把**自己那条命令**也匹配杀了
（命令行里含 `fnk`）—— 这正是 D-4 要解决的「按名字杀进程会误杀」的现场版。
后来改成先 `ps -eo pid,args | grep` 再按 pid 杀。
