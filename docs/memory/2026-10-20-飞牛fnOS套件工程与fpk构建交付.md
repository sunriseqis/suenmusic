# 2026-10-20 飞牛 fnOS 原生应用套件工程与 fpk 构建交付记录

## 一、交付背景与核心定位

在完成服务端单一真相源架构收敛（阶段 1-3）以及多代理全仓深度审计收敛（阶段 4）后，SuenMusic 服务端已具备单端口（3210）统一伺服 Web SPA 与流媒体 API 的全栈能力。

为使 SuenMusic 能够作为系统级**原生套件**入驻家庭 NAS 生态，我们在工程目录 `fn/` 中彻底摒弃 Docker 容器伪应用的包装模式，落地了针对 **飞牛私有云（fnOS）** 的 100% 纯原生应用套件工程，并通过官方 `fnpack` 命令行工具链实现了全自动化的一键打包流水线。

---

## 二、纯原生架构设计对比

| 维度 | Docker 伪应用模式（已废弃） | 纯原生套件模式（当前落地） |
| :--- | :--- | :--- |
| **执行模式** | 宿主机 Docker 后台拉取镜像创建容器 | Debian 12 系统级纯原生进程，直接运行 |
| **环境依赖** | 强依赖宿主机 Docker 守护进程与公网镜像拉取 | **零宿主依赖**，套件内置独立便携版 Node.js 22 运行时 |
| **性能损耗** | 容器网络桥接转发、虚拟化损耗 | **零虚拟化损耗**，原生 IPC/Socket 吞吐 |
| **存储映射** | 需要繁琐配置 UID/GID 权限、容器路径映射 | 飞牛原生 `data-share` 声明，`${TRIM_PKGVAR}` 目录直接读写 |
| **启动速度** | 需等待 Docker daemon、容器创建与端口绑定 | **秒级启动**，原生 Node 进程即刻常驻 |
| **图标与品牌** | 占位模板图标 | 采用官方 1024x1024 主图重采样高清抗锯齿图标 |

### 2. 自动化构建流水线 (`scripts/build-fn.mjs`)
- 支持一键执行 `node scripts/build-fn.mjs`；
- 自动读取根目录 `VERSION` 并归一化为 SemVer 版本号（`1.5` → `1.5.0`），自动同步至 `fn/manifest`；
- 从官方母版图标 `ios/App/App/Assets.xcassets/AppIcon.appiconset/AppIcon-1024.png` 通过 LANCZOS 滤波生成多尺寸高清 PNG；
- 自动准备便携版 Node.js 22.14.0 Linux-x64 二进制放入 `fn/app/bin/node`；
- 组装 `web/dist` 与 `server` 源码及生产依赖至 `fn/app/`；
- 调用官方 `fnpack build -d .` 自动构建输出并归档至 `output/suenmusic-v1.5.0.fpk`。

## 五、NAS 安装「设置目录权限失败」深度排查与彻底解决

真机手动安装 `.fpk` 报错「设置目录权限失败」，深入排查官方规范与系统行为后，定位到以下关键机理：

### 1. 深度根因分析（2026-10-20 当晚修正：真正主因是包内死链）
0. **app.tgz 内的自引用死链（真正主因，每版必报的根因）**：
   - `server/node_modules/.bin/` 有 15 个 npm 生成的 CLI 软链（tsc/semver/glob/qrcode…）；
   - `build-fn.mjs` 用 Node `fs.cp` 复制 node_modules，**fs.cp 会把 npm 的相对软链
     改写成构建机绝对路径**（`../typescript/bin/tsc` → `/home/suenmusic/.../tsc`）；
   - fnpack 打包时又只保留目标 basename → app.tgz 里变成 `tsc -> tsc` 自引用死链；
   - fnOS 安装遍历赋权时 `stat` 死链失败 → 界面**恒定**报「设置目录权限失败」，
     与改了多少版、NAS 有没有残留无关。
   - 修复：打包时删掉 `app/server/node_modules/.bin`（CLI 垫片运行时不依赖），
     并在 `assembleFpk` 前加 `assertNoSymlinks()` 硬校验（有软链直接失败不出包）。
1. **历史失败安装的物理目录锁死与残留（次因，首次失败后才有）**：
   - 首次安装失败后，fnOS 已经在用户的存储卷上创建了 `/vol*/@appcenter/suenmusic`、`/vol*/@appdata/suenmusic` 或 `/var/apps/suenmusic`；
   - 因安装未能正常走完回调，目录留在磁盘上，且所有者或 ACL 处于锁定状态；
   - 当用户再次上传新包安装时，fnOS 的 `appcenter` 守护进程尝试重建并赋权已有目录，导致底层直接抛出 `EEXIST` 或 ACL 拒绝，界面表现为**「依然目录设置权限失败」**。
2. **`config/privilege` 不能使用 `run-as: root`**：
   - 第三方原生应用若声明 `run-as: root`，fnOS 在准备 Windows ACL 权限时无法将包权限下发给普通应用隔离用户，权限校验阶段即被安全策略拦截报错；
   - 官方标准（对齐 `rustfs`、`adminer` 等官方第三方套件）要求统一使用 `{"defaults": {"run-as": "package"}}`。
3. **`config/resource` 的 `data-share` 冲突**：
   - 如果用户 NAS 本身已有同名共享文件夹或存储空间尚未完成 Windows ACL 适配（v1.2.0+ 存储空间提示“权限未适配”），任何声明了 `data-share` 的套件都会在创建共享目录时失败。
   - SuenMusic 的持久化数据完全存放在私有持久化目录 `${TRIM_PKGVAR}/data`（映射到 `@appdata`），不需要在文件管理器暴露共享文件夹，因此 `config/resource` 应当保持为 `{}`。
4. **`manifest` 平台字段规范化**：
   - 废弃已过时的 `arch = x86_64`，改为飞牛官方 `platform = x86`，并显式指定 `os_min_version = 1.1.0`。

### 2. 彻底解决方法
0. **删 .bin + 软链硬校验**（见上，主因）；
1. **应用包规范已全量对齐官方契约**：
   - `manifest`：`platform = x86`, `os_min_version = 1.1.0`
   - `config/privilege`：`{"defaults": {"run-as": "package"}}`
   - `config/resource`：`{}`
   - `cmd/main`：内置 `--experimental-strip-types` 原生运行 TypeScript
   - `cmd/install_callback`：标准 `exit 0`
2. **NAS 端操作指引（如果仍报残留错误）**：
   - 若在应用中心中能看到残留的 SuenMusic 卡片（处于已停止或异常状态），请先点击 **卸载**；
   - 若应用中心没有显示但仍报错，可通过 SSH 登录 NAS 执行清理残留应用目录：
     ```bash
     sudo rm -rf /var/apps/suenmusic /vol*/@appcenter/suenmusic /vol*/@appdata/suenmusic /vol*/@appconf/suenmusic /vol*/@apptemp/suenmusic /vol*/@apphome/suenmusic
     ```
   - 检查 **系统设置 > 存储空间管理**，确保目标存储池没有显示“权限未适配”（若有请按系统提示完成一次权限适配向导）。

## 六、安装验证与账号权限收尾（2026-10-20 当晚）

### 1. 死链修复验证通过

用户确认新版 `.fpk` **安装成功**（"搞定了终于"）。根因链条（fs.cp 改写软链 →
fnpack 只留 basename → 自引用死链 → fnOS 赋权 stat 失败）与修复手段
（删 .bin + `assertNoSymlinks()` 硬校验）见上文第五节，已验证有效。

### 2. fn 产物本就带全套账号权限（用户误判排查）

用户反馈"fn 产物的服务端没有账号管理能力"。实际核查：

- `fn/app/server/src/routes/admin.ts`、`db/migrations/018_user_roles.sql`、
  web dist 里的「账号管理」UI **全部在产物里**（build-fn.mjs 每次构建都从
  `server/src` 与 `web/dist` 现拷）；
- 用 fn 产物自带的 `bin/node` + 全新库实测：注册首个账号 → `role=admin`，
  `/api/admin/settings`、`/api/admin/users` 全部可用。

用户看不到能力的两种可能：① 库是旧构建建的（首账号停在 member，见下条修复）；
② 移动端宽度下「账号管理」在设置页的**高级** tab 里，桌面宽度才整页展开。

### 3. 真实缺口与修复（两个）

1. **注册通道不会自动收闭**：`registrationAllowed()` 在首号之后回落到环境变量
   默认值 `true`，等于永远敞开，与规划"注册完后由管理员决定开不开"不符。
   → `register()` 在首个账号落地时写 `allow_registration='0'`；
   管理员之后可在设置里重新打开。
2. **旧库升级后没有人是管理员**：018 之前建的账号，迁移加 `role` 列时全部落在
   默认值 `member`，升级后没人能进管理面（步骤 2 实施时就预警过）。
   → 新增迁移 `019_promote_first_admin.sql`：仅当库里一个 admin 都没有时，
   把最早注册的账号提成管理员（幂等）。已用"017 快照 + 无 role 列"的模拟旧库
   验证：迁移后首账号 role=admin。
