# 2026-10-24 版本号 2.0.0 落地 + versionCode 单一轴（Q9/Q10/Q11 全采纳）

## 改了什么

| 位置 | 改动 |
|---|---|
| `VERSION` | `1.6.0` → **`2.0.0`**（用户指定当前版本） |
| `scripts/build-hw.mjs` | versionCode 由 `20000+提交数` → `major*1000000+minor*10000+patch*100`；加 **fail-fast**：非三段式、`minor/patch ≥ 100`、越界 int32 一律 fail；产物名改 `suenmusic-<版本>.hap` |
| `scripts/build-ios.mjs` | 同上公式与 fail-fast（`MARKETING_VERSION` 仍取 `VERSION`） |
| `server/src/services/github-update.ts` | 新增导出 `versionCodeOf(versionName)`；拉取产物时写推导值；旧缓存 `versionCode=0` 时读取阶段现算 |
| `server/src/routes/update.ts` | `/api/update/check` 比对改**单一轴**（versionCode），任一侧拿不到 code 才退回版本名比较 |

## 实测（模拟器 + 服务端）

```
build-hw：当前目标版本 v2.0.0 / versionCode: 2000000 (major*1000000+minor*10000+patch*100 → 2000000)
hw/AppScope/app.json5：versionName 2.0.0 / versionCode 2000000
客户端设置页：检查更新 → v2.0.0
假 2.0.1（latest.json 里 versionCode 故意写 0 → 服务端推导 2000100）：
  /api/update/check → available=True，latest.versionCode=2000100；客户端行尾「新版本 2.0.1」并拉起浏览器
删掉假产物后再查 → available=False；客户端行尾「已是最新」
撞号守卫：VERSION=2.0.100 → 构建直接 fail「minor/patch 必须 < 100」
```

## 影响与注意

- 产物名从此是 `suenmusic-2.0.0.hap`（本地产物 = 发行名；包仍不签名，用户侧载）。
- 已装的 1.6.0（20175）在新公式下会被判旧（2000000 > 20175）—— 符合「不要求平滑升级」。
- 假 2.0.1 已清理，`server/data/updates/` 为空。
