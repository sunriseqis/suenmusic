# 2026-10-27 hw 端「蓝牙冷启动」调研（不实施）

> 命题：手机上连接蓝牙耳机/车机后，**应用未运行（冷启动）**也能自动拉起并开始播放。
> 结论先行：**第三方应用做不到真正的「蓝牙事件冷启动」**——HarmonyOS 把这条系统入口只留给系统应用。
> 下面给出证据、可行替代方案，以及需要真机确认的边界。

证据来源：`dsh-harmony-next` 技能包内置的离线 API 12–23 快照（Huawei 官方文档镜像），
路径前缀 `harmony-next/references/`。所有条款均可按文中文件名复查。

---

## 一、先澄清三种「冷启动」语义

| 语义 | 具体表现 | 是否可行（第三方） |
| --- | --- | --- |
| A. 事件冷启动 | 应用**进程不存在**，蓝牙连上那一刻系统拉起应用并播放 | ❌ 不可行（无可用入口） |
| B. 存活期自动播 | 应用在后台（长时任务挂着，进程存活），蓝牙连上自动续播 | ✅ 可行 |
| C. 一键唤回 | 用户按耳机/车机播放键，或点常驻通知/桌面卡片恢复播放 | ✅ 可行（最稳） |

---

## 二、关键证据（决定 A 不可行）

### 1. 静态订阅（StaticSubscriberExtensionAbility）是系统应用专属

`JsEtsAPIReference/guides/module.json5配置文件.md`（ExtensionAbility `type` 字段说明）原文：

> `staticSubscriber`：静态广播的 ExtensionAbility，**三方应用配置不生效，当前配置仅在系统应用中有效**。

同一段落里 `service` / `dataShare` 也标注「三方配置无法安装应用，需要申请特权，特权申请不对三方应用开放」。

**推论**：社区里流传的「用 StaticSubscriberExtensionAbility 订阅蓝牙设备事件、系统唤醒应用」方案，
对第三方应用无效（配置会被忽略，装包不生效）。这一点必须写清楚，避免后续被误导去实现。

### 2. 蓝牙连接状态确实是「公共事件」，但动态订阅要求进程存活

`JsEtsAPIReference/topics/misc/系统定义的公共事件.md`（API 20+）：

| 事件 | 值 | 订阅者所需权限 |
| --- | --- | --- |
| `COMMON_EVENT_BLUETOOTH_A2DPSOURCE_CONNECT_STATE_CHANGE` | `usual.event.bluetooth.a2dpsource.CONNECT_STATE_CHANGE` | `ohos.permission.ACCESS_BLUETOOTH` |
| `COMMON_EVENT_BLUETOOTH_A2DPSOURCE_AVRCP_CONNECT_STATE_CHANGE` | `usual.event.bluetooth.a2dpsource.AVRCP_CONNECT_STATE_CHANGE` | 同上 |
| `COMMON_EVENT_BLUETOOTH_HANDSFREE_AG_CONNECT_STATE_CHANGE` | `usual.event.bluetooth.handsfree.ag.CONNECT_STATE_CHANGE` | 同上 |
| `COMMON_EVENT_BLUETOOTH_A2DPSOURCE_CODEC_VALUE_CHANGE` | `usual.event.bluetooth.a2dpsource.CODEC_VALUE_CHANGE` | 同上 |

动态订阅（`commonEventManager`）只在进程存活时有效；要「进程不在也能收到」就必须静态订阅 → 回到第 1 条死路。

### 3. 轮询与事件 API 现状（`@ohos.bluetooth.connection`）

- `connection.getProfileConnectionState(profileId?)`：查 A2DP/HFP/HID 等 profile 的连接状态，需 `ohos.permission.ACCESS_BLUETOOTH`；
- 可用事件只有：`bondStateChange`（配对）、`bluetoothDeviceFind` / `discoveryResult`（扫描）、`batteryChange`、`pinRequired`；
- **没有一个通用的「某设备已连接」事件**（文档 `on()` 全集就这五个）。

也就是说：存活期监听只能靠「公共事件（API 20+）」或「定时轮询 `getProfileConnectionState`」。

### 4. workScheduler 不能当触发器

`JsEtsAPIReference/modules/ohos/@ohos.resourceschedule.workScheduler`：
> 对于循环任务，任务执行间隔**至少 2 小时**。

2 小时的粒度不可能实现「插上耳机就播」。

### 5. 后台启动 UIAbility 有系统约束

`JsEtsAPIReference/topics/misc/UIAbilityContext.md` 有「后台启动 Ability」的示例与前提条件；
后台任意拉起界面是受限行为，不能假设「订阅到事件就能弹界面」。

### 6. 音频后台播放本身是支持的（本仓库已具备）

`module.json5` 已声明：
```json5
"backgroundModes": ["audioPlayback"]
```
并持有 `ohos.permission.KEEP_BACKGROUND_RUNNING`；运行时需
`backgroundTaskManager.startBackgroundRunning(context, ['audioPlayback'], wantAgentObj)`
（见 `@ohos.resourceschedule.backgroundTaskManager` 文档；仓库 `AVSessionManager.ets` 已有对应实现）。

## 三、可行替代方案（按性价比排序）

### 方案 B：存活期自动播（推荐先做，成本最低）

前提：应用在后台挂着音频长时任务（本仓库已具备）。

```
动态订阅 usual.event.bluetooth.a2dpsource.CONNECT_STATE_CHANGE（API 20+）
  或 每 5–10s 轮询 connection.getProfileConnectionState(PROFILE_A2DP_SINK)
→ 检测到「未连接 → 已连接」跳变
→ 立刻恢复上次播放（复用现有队列 + 续播位置）
```

注意点：
- 需要 `ohos.permission.ACCESS_BLUETOOTH`（用户可拒绝，要降级为「不自动播」）；
- 要区分「设备切换」与「重新连接」，避免耳机摘下再戴反复起播；
- 只在前一次「因断开而暂停」时才自动播，用户手动暂停的不自动播（否则会被骂）。

### 方案 C：一键唤回（最稳，建议同时保留）

三条互不冲突的入口：
1. **AVSession 媒体控制**：耳机/车机/锁屏按播放键即恢复（现有 `AVSessionManager` 已注册）；
2. **常驻通知**：音频长时任务自带通知，点一下回前台；
3. **桌面卡片**：本仓库已有 `SuenFormAbility`，可加「继续播放」动作直达播放页。

### 方案 D：推送兜底（可选，非实时）

服务端在检测到设备上线时下发通知（Push Kit / `remoteNotification` 类型 ExtensionAbility），
用户点通知 → 拉起应用。缺点：不是「自动播」，且需要服务端与推送通道配合。

### 不可行清单（别再往这些方向试）

- ❌ `staticSubscriber` 静态订阅蓝牙事件（三方不生效）；
- ❌ 常驻 `service` / `dataShare` 类型 ExtensionAbility（需系统特权）；
- ❌ `workScheduler` 做连接触发（最小 2 小时）；
- ❌ 假设能无限后台常驻（系统会回收，长时任务也需符合 audioPlayback 语义）。

## 四、需要真机验证的边界（这次没做，只列清单）

1. 动态订阅 `usual.event.bluetooth.a2dpsource.CONNECT_STATE_CHANGE` 在**应用后台（长时任务中）**是否仍能收到；
2. 应用被系统回收后，用户按耳机播放键，系统是否会重新拉起本应用（媒体控制唤回能力的实际边界）；
3. `ACCESS_BLUETOOTH` 用户拒绝后，`getProfileConnectionState` 的返回与降级表现；
4. 车机（HFP/A2DP + AVRCP）与 TWS 耳机在断连/重连时的公共事件时序差异；
5. 元服务（atomic service）与普通应用在这些能力上的差异（本仓库是普通应用）。

---

## 五、结论与建议（本轮不实施）

1. **「应用没运行也能被蓝牙事件拉起并播放」在 HarmonyOS 第三方应用不可实现**，这是系统边界，不是实现难度问题；
2. 体验上最接近且工程可控的是 **B + C**：
   - B：存活期自动续播（公共事件或轮询 + 恢复播放）；
   - C：媒体控制/通知/桌面卡片的一键唤回；
3. 若产品坚持「完全自动」，唯一现实路径是**降低系统依赖**：把自动播做成「用户可选的开关」，并诚实告知「应用被系统清理后不会自动播」；
4. 与现有代码的结合点：`core/AVSessionManager.ets`（会话与播放状态）、`core/MediaPlayerCore.ets`（队列/续播）、`forms/SuenFormAbility.ets`（卡片动作）；新增内容只需一个「蓝牙状态监听器 + 自动播开关」，不改动播放内核。

> 本次仅调研，未改任何代码。
