# 2026-10-27 hw 端「蓝牙冷启动」调研（v2 · 推翻 v1 结论）

> **v1 结论作废**。v1 只证明了「静态订阅（staticSubscriber）三方不可用」，却把它推广成
> 「第三方应用做不到」——这是错的。酷狗 / 网易云 / QQ 音乐在鸿蒙上确实能「连上蓝牙耳机就播放」，
> 说明入口不在静态订阅，而在**系统媒体框架**。

---

## 一、v1 错在哪

| v1 的判断 | 实际情况 |
| --- | --- |
| 「staticSubscriber 三方不生效」 | 这条本身没错（module.json5 文档明写：仅在系统应用中有效） |
| 「所以第三方无法被蓝牙事件拉起」 | **推论错误**。蓝牙不是唯一唤醒源，媒体会话（AVSession）才是 |

耳机连上/按键 → 系统媒体框架 → 唤起「最近播放过的媒体应用」，这条路不需要应用自己订阅蓝牙事件，也不需要常驻。

---

## 二、三条真实机制（按证据强度排序）

### 机制 A：AVSession 媒体会话 + 系统媒体控制托管（最可能是主路径）

~~~
应用起播过一次 → 建立 AVSession 并 setAVPlaybackState / setAVMetadata
→ 应用退出/被系统回收后，系统接管会话（控制中心/锁屏/耳机 上仍显示播控卡片）
→ 蓝牙耳机连接建立（AVRCP）或按下播放键
→ 系统向该会话下发 play → 拉起所属应用（冷启动）→ 应用恢复播放
~~~

这与 iOS Now Playing、Android MediaSession 的既有行为一致，也是普通音乐 App 在鸿蒙上
「连上耳机就播 / 按一下耳机就播」最省力的解释：应用什么都没订阅，是系统来拉起它。

对代码的意义：不需要新权限、不需要常驻；需要把 AVSessionManager.ets 做扎实 ——
元数据、播放态、可用命令、播放位置必须持续同步（系统卡片依赖这些字段决定显示与按键行为）。

### 机制 B：后台存活 + A2DP 连接状态公共事件（应用还在后台时秒起播）

离线快照可查（JsEtsAPIReference/topics/misc/系统定义的公共事件.md，API 20+）：

| 事件 | 值 | 权限 |
| --- | --- | --- |
| A2DP 源连接状态 | usual.event.bluetooth.a2dpsource.CONNECT_STATE_CHANGE | ohos.permission.ACCESS_BLUETOOTH |
| AVRCP 连接状态 | usual.event.bluetooth.a2dpsource.AVRCP_CONNECT_STATE_CHANGE | 同上 |
| HFP AG 连接状态 | usual.event.bluetooth.handsfree.ag.CONNECT_STATE_CHANGE | 同上 |

应用在后台（backgroundModes: audioPlayback + KEEP_BACKGROUND_RUNNING 保护下未被挂起）时，
动态订阅这些事件是可行的，收到即起播 —— 这是「零延迟」体验的来源。
（v1 说「动态订阅要求进程存活」是对的，但漏了：音乐应用靠音频长时任务本来就长期存活。）

### 机制 C：系统/合作白名单

系统音乐或与华为深度合作的音乐应用，可能拿到「蓝牙连接自动播放」的系统级能力（三方不可申请）。
判据：若某 App 在从未播放过的情况下连耳机也能自动播，那必然是 C。

---

## 三、怎么把 A / B / C 区分开（可执行实验，需真机）

本机模拟器没有蓝牙音频设备，以下实验必须在真机上做：

| 现象 | 结论 |
| --- | --- |
| App 从未播放过，连耳机就自动播 | 只能用机制 C（系统白名单），我方无法复刻 |
| App 播放过，被强杀后连耳机/按播放键 → 被拉起并续播 | 机制 A（媒体控制托管） |
| App 在后台未被杀 → 连耳机立刻播（无按键） | 机制 B（A2DP 公共事件） |

### 实验步骤（先验 A）

~~~bash
# 1) 起播一首，确认 AVSession 建立
hdc shell hilog -r && hdc shell hilog | grep -iE 'AVSession|MediaControl'

# 2) 强杀进程（模拟冷启动前状态）
hdc shell aa force-stop com.suenmusic.app

# 3) 连接蓝牙耳机，然后按耳机播放键

# 4) 观察是否被系统拉起（关键在 startAbility / EntryAbility onCreate 来源）
hdc shell hilog | grep -iE 'SuenMusic|AVSession|MediaControl|A2dp|startAbility'
~~~

日志里若出现「媒体控制 / AVRCP → 拉起 EntryAbility」的痕迹，则机制 A 成立，
我们要做的就是**把 AVSession 的元数据/播放态/命令集合补全**，而不是订阅蓝牙。

### 对照实验（最有力）

同一台真机装 QQ 音乐，重复上述步骤，对比 hilog 中是谁在拉起它（系统媒体服务 vs 应用自身进程）。

## 四、若机制 A 成立，需要补什么（草图，未实施）

| 项 | 现状 | 需要补 |
| --- | --- | --- |
| AVSession 元数据（标题/歌手/封面/时长） | 已有基础实现 | 换曲、换封面、时长变化都要及时 setAVMetadata |
| 播放状态（位置/速度/循环模式） | 部分 | setAVPlaybackState 要含 position + speed + loopMode |
| 支持的媒体命令 | 未确认 | setSupportedCommands([play, pause, stop, playNext, playPrevious, seek]) |
| 会话保活 | 未知 | 确认长时任务结束时不要 destroy() 会话 |
| 冷启动恢复点 | 有续播能力 | 被系统拉起后直接续播（读上次队列 + 位置），不要停在首页 |

## 五、机制 B 若也要做（后台时秒起播）

~~~
申请 ohos.permission.ACCESS_BLUETOOTH（用户可拒，拒绝则退化为机制 A）
动态订阅 usual.event.bluetooth.a2dpsource.CONNECT_STATE_CHANGE
→ 检测「未连接 → 已连接」跳变
→ 若上次是「因断开而暂停」则自动续播；用户手动暂停的不自动播
~~~

## 六、本轮调研边界（诚实标注）

- 在线官方文档本轮无法访问（Bing / DuckDuckGo / r.jina.ai 全部被挡），因此
  「系统媒体控制能否拉起已退出应用」这条**没有拿到官方原文**，属机制推演 + 行业一致性证据；
- 离线快照（dsh-harmony-next，API 12–23）只能证明：staticSubscriber 三方不可用、
  蓝牙连接状态公共事件存在且需 ACCESS_BLUETOOTH、workScheduler 最小 2 小时；
- 模拟器无蓝牙音频设备，机制 A/B 的判定必须真机 + 蓝牙耳机，步骤见第三节。

> 本次仍不实施代码。下一步建议：真机跑第三节实验，再决定补 AVSession（低成本、无新权限）还是加 A2DP 订阅。
