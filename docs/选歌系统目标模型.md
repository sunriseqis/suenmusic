# 选歌系统目标模型

> **性质**：长期资产，**不随迭代废弃**。本文件是选歌系统从建库到消费的**目标形态档案**，
> 验收以本文件为准，未来的优化以本文件为模板续写。
> 当某个阶段完成后，在「阶段状态」标记 ✅ 并写下**实际落地与设计的差异**（不要事后修改设计本身）。
>
> 相关：[2026-10-29 建库审计与选歌约束评审](memory/2026-10-29-建库审计与选歌约束评审.md)、
> [2026-10-29 建库与选歌约束优化](plan/2026-10-29-建库与选歌约束优化.md)

## 〇、设计哲学（三条不变量）

1. **规则写在数据/建池层，不是提示词**
   AI 会把「减少推荐」理解成「那就推 2-3 首」。**模型看不见就不会违反**。
   提示词只做「语气与格式」，数量与频次约束一律在建池层硬性过滤。

2. **信号分正负，且都有动机**
   · 收藏 = 强正（用户主动留下的）
   · 听过但未收藏 = 弱负（动机：听腻 / 不喜欢 / 没想起来）
   三者综合定熟悉度，不能只看收藏量。
   **⚠️ 历史记录与播放记录不作为任何建库/选歌的参考依据**（2026-10-29 用户裁定），这两条数据不需要记录。

3. **AI 的每一份输出都要有消费方**
   推荐理由给前端展示一次 = 浪费。审核当筛子 + 精炼器，理由才有价值。

## 一、阶段 A：建库（从外部三源采数据进本地库）

### A.1 什么时候建

| 触发 | 时机 | 说明 |
| :-- | :-- | :-- |
| **闲时窗口** | 每天凌晨 **1:00-6:00**（2026-10-29 用户调整，原 3:00-6:00） | **唯一允许外网建库的窗口**。白天严禁后台打 QQ（避免 2001 限流影响用户前台搜索） |
| **每日维护** | 每天 00:30（业务本地时间） | `runDailyMaintenance` 跑完选歌后顺带 `kickLibraryBuilder` |
| **池子健康检查** | 每 10 分钟 | `library-topup` 看哪个来源低于健康线，低了就补（不受夜间窗口约束，**多源主源是酷狗**） |
| **用户行为触发** | 收藏歌手/导入歌单时 | 立即 `enqueueBuildJob` 入队，由 `kickLibraryBuilder` 调度（2026-10-29 用户修正：**建库必须被用户行为触发**，不能完全依赖定时） |

### A.2 怎么建

```
种子歌手（收藏歌手按收藏数分档）
      ↓
建库队列（library_build_queue）
      ↓
调度器（library-builder.ts runLoop）
      ↓
  本地回填优先（零网络）→ 本地保底 + **继续走多源补源**（不能短路）
      ↓
  未命中才走外网：酷狗（主）→ 网易云（辅）→ QQ（兜底）
      ↓
  落库 library_tracks（带 id 前缀：qq_/kg_/ne_）
```

**硬约束**：
- 本地回填**绝不 return**（只作保底，不能作替代）
- 对 `hot_fetched_at` 早于「多源上线时间」的歌手**强制重拉**（否则历史快照永远不更新）
- 外网特遣：单轮最多 2 个、间隔 4 秒、仅夜间 1:00-6:00（QQ 限流防御）
- 曲目筛选：`VARIANT_RE`（变种/翻唱/纯音乐/伴奏）+ `isCoverOrInstrumental` + 酷狗 `isOriginal`/网易云 `originCoverType===1`
- **多源去重（2026-10-29 用户要求）**：同一首歌在三源里都存在时**只入库一次**，id 归一（以首个命中的源为准），避免同曲多副本污染库

### A.3 谁来建

**三类角色，自动化为主**：

| 角色 | 职责 |
| :-- | :-- |
| **建库器（library-builder）** | 调度队列、调多源、落库。全自动，无需人工 |
| **补库器（library-topup）** | 每 10 分钟看池子健康线，低了自动补 |
| **用户** | 通过收藏/导入歌单间接提供种子；通过「不喜欢」过滤黑名单 |

### A.4 种子歌手分档（阈值 5，2026-10-29 用户裁定）

> **口径**：建库是**三源合并**（酷狗/网易云/QQ），不是只 QQ。下面所有分档与阈值都是在三源之上生效的。

| 收藏数 | 定性 | 处理 |
| :-- | :-- | :-- |
| 1-2 首 | 只喜欢这几首歌 | **只作曲风参考**，不当歌手种子 |
| 3-4 首 | 算喜欢 | 可以推，新歌优先 |
| ≥5 首 | 深度喜欢 | 进 TOP 池、新歌必推 |
| ≥10 首 | 巨量（筛过的） | TOP 池 + 降频，新歌必推 |

### A.5 落地产物

| 表 | 内容 |
| :-- | :-- |
| `library_tracks` | 建库曲目（id 前缀标识源） |
| `library_artists` | 歌手档案（mid / name / hot_fetched_at） |
| `library_user_artists` | 用户-歌手关联（origin 标记来源） |
| `artist_simi_cache` | 相似歌手表（**仅作发散输入之一**） |
| `user_style_profile` | **曲风画像**（按单曲标签统计，已存在但未被召回/决策读取） |
| `tracks` | 曲目元数据（含未入库的搜索结果） |

### A.6 阶段 A 验收

- [ ] `library_tracks` 的 id 前缀分布含 `kg_` / `ne_`，且三源都有 >0
- [ ] 本地回填后**仍有多源补源**（看 `[多源建库]` 日志）
- [ ] 新歌识别覆盖「收藏 ≥5 的歌手」，而非只看全站榜单

## 二、阶段 B：选歌（从库里挑今日推荐）

### B.1 什么时候选

| 触发 | 时机 | 说明 |
| :-- | :-- | :-- |
| **每日定时** | 每天 00:30（业务本地时间） | `runDailyMaintenance` 跑一次 |
| **用户首次打开** | 新用户冷启动 | **分三种情况**（见 B.1.1） |
| **上一份被操作过** | 每日维护判定 | 播放过列表里任意一首、或对某首歌/歌手点过不喜欢 → 重新生成 |
| **上一份没动** | 每日维护判定 | 顺延沿用（date 改成今天） |

### B.1.1 新用户首次打开（2026-10-29 用户裁定）

**分三种情况**，不是一律走 AI：

| 情况 | 判定 | 处理 |
| :-- | :-- | :-- |
| **有其他用户** | 库里已有其他用户的历史歌单 | **直接复用其他用户的现有歌单**（不走 AI，秒出） |
| **没其他用户但有库** | 没有历史歌单但 `library_tracks` 有数据 | **不经过 AI，随机找 40 首**（保证新用户一开就有内容） |
| **全新安装** | 没库、没歌单 | **不做任何操作**。前端客户端仅显示「还没有偏好的歌曲，收藏多了以后再尝试为你推荐」类似说明 |

**目标**：新用户首次打开永远有可看的内容（前两种），或至少有明确的「为什么没有」说明（第三种），
不要让用户看到空白页面或转圈。

### B.2 怎么选

```
候选池（5 路来源，POOL_MAX=120）
      ↓
建池层硬约束过滤（模型看不见被禁的）
      ↓
选歌 AI 选 30-40 首 + 写长理由（给审核看）
      ↓
归类说明 → 审核 AI 判断（成立：写 AI 黑名单；不成立：同池重选）
      ↓
落地：存 ai.daily.active:<userId>（含快照）
      ↓
审核 AI 第二轮：判断 + 精炼（approved → 短句；rejected → 丢掉）
      ↓
前端消费（推荐语页 / 每日推荐页 / 首页）
```

### B.3 谁来选

| 角色 | 职责 | 输入 | 输出 |
| :-- | :-- | :-- | :-- |
| **建池器（ai-recall）** | 从库里取候选、过滤 | 5 路来源 + 硬约束 | `candidates[]` |
| **选歌 AI（ai-decide）** | 从候选池挑、写长理由 | 长期口味记忆 + 偏好摘要 + 曲风画像 + 候选池 | `{picks: [{id, reason_for_review}]}` |
| **审核 AI（ai-review）** | ① 判断归类说明是否成立 ② 判断理由是否在水 + 精炼 | picks + 画像 | 归类 verdict / 每首 verdict + `reason_for_display` |
| **欢迎语 AI（ai-welcome）** | 单独一回合写欢迎语/导语 | 画像 + 偏好摘要 | `welcomePhrase` + `greeting` |

### B.4 候选池（5 路来源）

| 来源 | 占比 | 说明 |
| :-- | --: | :-- |
| simi（相似歌手） | 50% | **发散基础必须是「曲风 + 相似歌手」双路**，不能纯按歌手 |
| playlist（网友歌单） | 25% | 按收藏曲目 tag 匹配，不按歌手名 keyword |
| seedOld（本尊老歌） | 15% | 收藏歌手的旧歌 |
| chart（巅峰榜） | 10% | 全站热榜 |
| seedNew（本尊新歌） | 不占名额 | 收藏 ≥5 的歌手新专辑，**必进** |

**建池层硬约束（模型看不见就不会违反）**：

- 一位歌手最多 1 首
- **TOP 歌手**（收藏 ≥10）：每几天最多 1 位 1 首老歌（2026-09-22 用户拍板）
- **收藏 1-2 首的歌手不进 TOP 池**（只作曲风参考）
- 已收藏（永久排除）/ 7 天内推过 / 用户黑名单物理拦截
- 翻奏 / 纯音乐不入池

### B.4.5 「曲风参考」维度的参考物（2026-10-29 用户提出）

**问题**：原计划说「收藏 1-2 首的歌手只作曲风参考」，但**曲风参考没有参考物**——
建库阶段根本不知道「这首歌是什么曲风」，更不知道「用户喜不喜欢这种曲风」。

**解法**：用**曲风画像**（`user_style_profile`，按单曲标签统计）当参考物，链路是：

```
曲目标签（ai-tags，受控词表）
      ↓
  聚合出 user_style_profile（用户风格分布，已有）
      ↓
  按 tag 匹配「曲风相近」的歌 → 喂给候选池的 simi 来源
```

**建库阶段**也要能判断曲风（不能只在选歌阶段才打标）：
- 建库入库时**同步打标**（`ai-tags` 服务已存在，受控词表）
- 标签作为 `library_tracks.payload_json` 的一部分落库
- 选歌阶段按标签过滤/加权，不再依赖「歌手相似」

**用户喜不喜欢这种曲风**的判定：从收藏曲目的标签分布反推（标签出现在收藏里的频次 = 喜好度）。

### B.5 未收藏 = 弱负信号

```
同一歌手「听过但未收藏」越多 → 冷却期越长（不一刀切）
候选池里同歌手的歌，按「用户收藏率」降权（不取消资格，给「没想起来」留口子）
```

### B.6 选歌 AI 的输出格式

```json
{'picks': [{'id': 'xxx', 'reason_for_review': '长理由（详细听感，给审核看）'}]}
```

**硬约束**：严格 JSON / id 原样回填 / 数量刚好 / 同歌手 1 首 / 本尊新歌必进 / 金曲 ≤5。

### B.7 审核 AI 的双轮职责

**第一轮（归类审核，`reviewExclusions`）**：
模型说「候选池没货了」时的唯一闸门。
- 成立 → 写 AI 黑名单，本批池子作废，换新池
- 不成立 → 带审核意见从同一批池子重选

**第二轮（理由审核 + 精炼，2026-10-29 新增）**：
用户原话：「选歌的 AI 负责给理由，前端的部分由审核给。审核觉得选歌 AI 某首歌的推荐写的非常合理
而且强烈认可，那么可以落进本歌曲的推荐语页，如果觉得完全在水，那就丢掉，不给前端看。」

```json
{'reviews': [{'id': 'xxx', 'verdict': 'approved', 'reason_for_display': '压缩后短句'}]}
```

`approved` → 精炼成 12-25 字短句，落进「这首歌的推荐语页」
`rejected` → **丢掉，前端不展示理由**（歌还在，只是没推荐语）

### B.8 阶段 B 验收

- [ ] 候选池里 TOP 歌手（收藏 ≥10）每天 ≤1 位，老歌 ≤1 首
- [ ] 收藏 1-2 首的歌手**不出现在 TOP 池**，只在曲风参考维度
- [ ] 新歌（收藏 ≥5 的歌手发片）在 24h 内被识别
- [ ] 选歌 AI 的 `reason_for_review` 是详细听感（不是空话）
- [ ] 审核 `approved` 的 `reason_for_display` 是 12-25 字短句
- [ ] 审核 `rejected` 的前端不展示理由

## 三、阶段 C：AI 输出内容总览

### C.1 五类 AI 输出

| 输出 | 由谁写 | 什么时候写 | 存哪 | 给谁消费 |
| :-- | :-- | :-- | :-- | :-- |
| **选歌理由**（长） | 选歌 AI | 每天 00:30 选歌时 | `ai.daily.active:<userId>` 的 `reason_for_review` | 审核 AI |
| **推荐语**（短） | 审核 AI | 选歌后立即精炼 | 同上 `reason_for_display` | **前端**：每日推荐页、歌曲推荐语页 |
| **欢迎语**（`welcomePhrase`） | 欢迎语 AI | 选歌后单开一回合 | 同上 `welcomePhrase` | **前端**：首页大字 |
| **导语**（`greeting`） | 欢迎语 AI | 同上 | 同上 `greeting` | **前端**：每日页标题 |
| **画像**（persona） | 画像 AI（ai-memory） | 收藏/不喜欢后 1 小时尾部防抖 | `ai_memory.summary:<userId>` | 选歌 AI 的输入 |

### C.2 画像内容

```
ai_memory.summary:<userId>
  = 长期口味画像（Markdown）
    核心审美基调（Anchor Artists）—— 易听觉疲劳，低频偶遇
    收藏较多的其他歌手 —— 次熟悉
    最近收藏的歌曲
    最近的操作（权重最高）
    曲风标签分布（user_style_profile）
```

`ai_memory.guidance:<userId>` = 用户对画像的微调指令（如「别过度解读」）

### C.3 问候语/欢迎语内容

```
welcomePhrase：6-20 字，首页大字，句末必须有标点
greeting：≤60 字，3-8 字短语开头 + 中文逗号，逗号前是每日页主标题
```

**硬性禁止**：歌单/推荐/继续/照旧/老规矩/为主/主打/挑选/精选/入选/曲目/这批/这轮
**硬性禁止**：歌手名/歌曲名/专辑名（那是选曲的活）
**硬性禁止**：时段套话（早上好/中午好/晚上好/夜深了，代码兜底）
**必须**：第一人称「我」对「你」，禁止第三人称

### C.4 其他 AI 输出

| 输出 | 由谁写 | 用途 |
| :-- | :-- | :-- |
| **收藏页 slogan** | ai-memory | 收藏页品味洞察评语（20-35 字），`ai.favorites.slogan:<userId>` |
| **曲目标签** | ai-tags | 受控词表打标（数据地基），供召回用 |
| **归类说明审核** | ai-review | 判断模型「没货了」是否成立 |
| **否定反馈摘要** | ai-rejection-digest | 把用户黑名单浓缩成提示词片段 |

## 四、阶段 D：前端消费

### D.1 展示什么

| 位置 | 内容 | 来源 |
| :-- | :-- | :-- |
| 首页大字 | `welcomePhrase` | 欢迎语 AI |
| 每日页标题 | `greeting` | 欢迎语 AI |
| 每日推荐页 | 40 首曲目 + 每首 `reason_for_display` | 选歌 AI + 审核精炼 |
| 歌曲推荐语页 | 单曲的 `reason_for_display` | 同上 |
| 收藏页 | `ai.favorites.slogan` | ai-memory |
| 画像面板 | `ai_memory.summary` | ai-memory |

### D.2 不展示什么

- 审核 `rejected` 的理由（只显示歌，不显示推荐语）
- 长理由（`reason_for_review`）—— 这是审核的输入，不是用户的
- 归类说明、AI 黑名单、模型思考过程

### D.3 用户反馈回路

| 用户行为 | 系统反应 | 写入 |
| :-- | :-- | :-- |
| 收藏 / 加入歌单 | 强正信号，进种子歌手 | `favorites` |
| 播放完 / 中途跳过 | 完播率供疲劳判定 | `play_history`（`completed`/`played_ms`） |
| 不喜欢 / 移除 | 物理拦截 | `user_dislikes` |
| 跳过当前曲目 | 7 天内不重推 | `recommend_history` |
| 手动调优画像 | 画像 AI 微调 | `ai_memory.guidance` |

### D.4 阶段 D 验收

- [ ] 每首歌的推荐语是审核认可版，不出现模板空话
- [ ] 欢迎语/导语是完整通顺的一句，无歌单策展口吻
- [ ] 不喜欢/跳过的歌 7 天内不重推
- [ ] 审核 `rejected` 的前端不展示理由

## 五、阶段 E：维护

| 项 | 规则 |
| :-- | :-- |
| 推荐历史 | 7 天冻结（用户拍板） |
| **历史记录/播放记录** | **不作为建库/选歌参考**（2026-10-29 用户裁定），这两条数据不需要被记录 |
| 库健康线 | simi 300 / playlist 150 / seedOld 120 / chart 60，低于就补，补到 1.5 倍停 |
| 每日维护 | 00:30 跑 `runDailyMaintenance`：上一份「被操作过」→ 重新生成，否则顺延 |
| 画像更新 | 收藏/不喜欢后 1 小时尾部防抖 |
| 运维日志 | `ops_logs` 表（三维度：音源解析 / Cookie / AI），保留 7 天 |
| AI 健康 | `ai.health`（连续失败次数、上次失败原因） |
